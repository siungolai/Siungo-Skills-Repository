# 交叉验证方法（cross-validation）

> `SKILL.md` §4 讲的是「为什么要交叉验证」，本文件讲「四条路各自怎么取证、取证时的具体坑、结论怎么定级」。

---

## 一、四条取证路径

| 路径 | 证据形态 | 典型位置 | 难度 | 独立性 |
|---|---|---|---|---|
| ① 官方接口表 | **位图** | 文档站产品页、仓库 `docs/` | 高（要读图） | 低（与官方源码同源） |
| ② 上游 BSP 源码 | 文本 | `main/user_config.h`、`components/port_bsp/*.cpp` | 低（可 grep） | 低 |
| ③ 上游第三方框架配置 | 文本 | 仓库 `examples/esphome/*.yaml` | 低 | 低（但引脚写成了配置，最易比对） |
| ④ 外部项目板级配置 | 文本 | 第三方固件仓库的 `config.h` / `config.json` | 中（要找对仓库分支） | **高**（独立实现，最能暴露矛盾） |

**独立性排序**：④ > ① ≈ ② ≈ ③。

前三条都出自上游团队，可能一起错。④ 是别人照着官方文档写的——他会漏抄、会按自己板子改，这恰恰是它作为对照的价值。

## 二、路径①：位图接口表的还原

官方引脚表常常是图片，只能读图。还原步骤：

1. **定位网格线**——找出图里的横竖网格线像素，得到列边界与行边界坐标；
2. **读表头**——表头在第一行（或第一列），每一列的名字决定这一列的语义（`LCD` / `USB` / `RTC` / `SD` / 某编解码芯片 / `SYS` / `OUT`）；
3. **逐格归列**——按格子的 x 区间确定它属于哪一列；
4. **逐行读值**——按 y 区间确定行号（通常第一列是 GPIO 编号）。

**三个必须验的点**：

- **表头对齐**：先确认第一列确实是 GPIO 编号列。表头错位会让整张表的语义全乱，而每一格看起来都「读得出来」。
- **空单元格**：读出空格的行不是「没有内容」，可能是「这一行在该列下没标信号」，也可能是「图片分辨率不够漏印了」。空行要单独核。
- **表里列出的器件未必装了**：见下节。

## 三、路径①的陷阱：表里的器件可能不存在

**实测案例**：某官方接口表有一列专门给「某 6 轴 IMU」预留，表里把 ESP32 的 I2C 引脚同时画在该列与扩展排针列。看起来板上装了 IMU。

**核对方法**：在原理图网表里检索该器件的型号串与常见别名（`QMI` / `8658` / `IMU` / `Accel` / `Gyro`）。全部零命中 → 板上**没有这颗器件**，那一列只是复用了同一组 I2C 信号的标注。

**结论**：官方接口表描述的是**信号分配**，不是**物料清单**。表里出现某列 ≠ 板上焊了对应器件。

**同类情况**：丝印标得清清楚楚但官方文档与代码里都没有对应实现的硬件（本次遇到的是板上的拨码开关）——这种也不进事实表，只记不确定项。

## 四、路径②：源码取证的定位技巧

固件源码里的事实分布在几个固定位置：

| 要找的 | 通常在哪 |
|---|---|
| 引脚宏定义 | `main/user_config.h` 的 `#define` 段 |
| 显示端口参数 | `components/port_bsp/display_bsp.cpp` 的构造函数调用（形参顺序即 MOSI/SCL/DC/CS/RST/宽/高） |
| 初始化序列 | 同文件的 `RLCD_Init()`，按 `0x` 命令码逐条抄，顺序即执行顺序 |
| I2C / I2S 引脚 | `components/ExternLib/codec_board/board_cfg.txt`（板级配置节） |
| 设备地址 | `components/port_bsp/codec_bsp.h` 的 `xxxAddress` 常量 |
| 存储配置 | `components/port_bsp/sdcard_bsp.cpp` 的构造函数默认值（clk/cmd/d0/width） |
| 按键 | `components/port_bsp/button_bsp.c` 的 `xxx_KEY_PIN` 与有效电平 |

**抄初始化序列时要连时序一起抄**——复位后的延时、命令之间的等待，漏掉延时在真机上表现为「偶尔不亮」。

**分辨率陷阱**：同一个仓库里，`user_config.h` 写竖屏 300×400，而 `main.cpp` 的构造函数传的是横屏 400×300。两者**同时存在且都正确**（一个是配置宏，一个是实际传给驱动的值）。遇到这种情况，两个都记并注明差异，**不替官方选一个**。

## 五、路径④：找第三方项目

常见形态：某个开源语音助手项目为这块板做了适配，仓库里有 `main/boards/<厂商>/<型号>/config.h`。

**取法**：
1. 找上游文档里提到的第三方项目名；
2. 在该项目的仓库里按板型目录名找——注意路径会随版本变化（旧版是 `main/boards/...`，新版可能是 `main/main/boards/...`），直接按目录名拼 URL 会 404；
3. 拿 `raw` 内容接口取文件，比走 API 稳。

**这一路能证明什么**：它证明「有第三方按这个引脚表做出了能跑的东西」。它证不了「官方文档是对的」——但当它与前三路一致时，四路对齐的可信度就很高了。

## 六、结论定级

| 定级 | 条件 | 写法 |
|---|---|---|
| 四方交叉验证 | 四路全部取到值且逐项一致 | 直接陈述事实 + 四处出处 |
| 多数一致 | 三路一致，第四路缺席或该路无此器件 | 陈述事实 + 注明第四路为何缺席 |
| 双源一致 | 两路一致，且其中一路是权威级 | 陈述事实 + 两处出处 |
| 待判定 | 只有参考级来源支撑 | 进不确定项，不进事实表 |

**定级要写进文档**，不要只在心里知道。读者需要知道某条结论的证据强度，才能决定敢不敢依赖它。

## 七、冲突的处理

发现两方冲突时，按这个顺序判：

1. **谁更新**——上游 commit 时间、文档页采集时间；
2. **谁更接近实物**——原理图 > 源码 > 文档正文 > 第三方配置；
3. **是不是描述了不同的东西**——「竖屏 300×400」与「横屏 400×300」不是冲突，是两处不同的配置。

三条都判不出来 → 进不确定项，写明冲突双方与判定条件。

## 八、读图与网表的具体坑

### 位图表格

- 表头错位 → 整表语义全错，且每一格都「读得出值」，最难发现。**先验表头**。
- 网格线漏检 → 行/列边界偏移，表现为「某行读出来是上一行的内容」。

### 原理图网表

PDF 文本层按绘制顺序而非电气连接顺序输出，抽取出的网表会出现：

- **引脚编号错位**——符号引脚号与网名的对应关系可能整体偏移一位或几位。**症状**：连接器的 FPC 脚序看起来完全合理，但和原理图上的印刷脚号对不上。
- **假大网**——某个网挂着几十上百个引脚，那是文本顺序问题不是真实连接。

**处置**：一旦发现编号错位，**该连接器的具体脚序不作为事实发布**，只发布「信号集合 + 连接器型号」，并明确提示接插件前对照原理图 PDF 复核。宁可少一条，也不要一条看着精确却错的脚序——脚序错一次，接插件就可能烧板子。
