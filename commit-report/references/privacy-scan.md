# 隐私与凭据扫描

`§2.5` 与 `§6.7` 的实施细则。**只对本次暂存内容判定**（`git diff --cached -U0` 的 `+` 行），不追溯已推送历史——历史是既成事实，处置见 §5。

## 1. 四级分类

| 级别 | 含义 | 处置 |
|---|---|---|
| 🔴 硬阻断 | 凭据明文、私钥、真实 SSID / 密码 / 监控 key | **不进入审阅**，直接报告并停 |
| 🟠 需确认 | 能定位到具体机器或人的标识 | 列进审阅；回复 ① 即视为认可 |
| 🟡 提示 | 可推断但不直接暴露 | 只列，不阻塞 |
| 🟢 放行 | 环回、文档段、占位符、虚构样本 | 完全不报 |

### 1.1 🔴 硬阻断

- 私钥块：`-----BEGIN (RSA |EC |OPENSSH )?PRIVATE KEY-----`
- 云厂商与平台令牌：`AKIA[0-9A-Z]{16}`、`LTAI[0-9A-Za-z]{12,}`、`gh[pousr]_[A-Za-z0-9]{36}`、`sk-[A-Za-z0-9]{20,}`、`xox[baprs]-`
- JWT：`eyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\.`
- 凭据赋值：`(password|passwd|pwd|secret|token|api[_-]?key|access[_-]?key)\s*[:=]\s*["'][^"'\s]{8,}`
- 凭据文件本身进暂存区（`secrets.h` 一类，`.example` 模板除外）
- **真实值复现**：从本机 gitignored 的 `secrets.h` 现读 `WIFI_SSID`、`WIFI_PASS`、`MONITOR_KEY` 等宏的值（长度 ≥4 的才参与），用 `grep -F` 比对暂存行。钩子与审阅里都不存秘密，值在运行时读。
  - 只扫这几个真正敏感的宏。主机名一类的宏（如 `RLCD_DATA_HOST`）是刻意公开的域名，扫了会天天误报。

### 1.2 🟠 需确认

- **公网 IPv4**：不在 `10/8`、`172.16/12`、`192.168/16`、`127/8`、`169.254/16`，也不在 RFC 5737 文档段 `192.0.2/24`、`198.51.100/24`、`203.0.113/24` 之内
- **公网 IPv6**：不在 `::1`、`fe80::/10`、`fc00::/7`、`2001:db8::/32` 之内
- **内网 IPv4 加具体网段**：`192.168.31.137` 本身就能推断家庭/办公拓扑与设备数
- **真实 MAC**：真实 OUI 前缀（虚构样本见 §1.4）
- **邮箱 / 手机号**：`[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}`、`1[3-9]\d{9}`
- **真实 SSID / 主机名 / 系统用户名**：`C:\Users\<name>\`、`/home/<name>/`、串口日志里的 `ssid=`
- **第三方主机名加非标端口**：`host.tld:12345`

### 1.3 🟡 提示

自有域名、服务器角色描述、内网路径、版本号——可推断，但通常已在别处公开。

### 1.4 🟢 放行

- `127.0.0.1`、`0.0.0.0`、`localhost`、`::1`
- RFC 5737 文档段、`example.com` / `example.org` / `example.net`
- 占位符：`<ssid>`、`<password>`、`<monitor-key>`、`<tcp-host>:<port>`、`<公网IP>`、`your-ssid`
- 虚构 MAC：`12:34:56:78:9A:BC`、`AA:BB:CC:DD:EE:FF`、`00:00:00:00:00:00`、`FF:FF:FF:FF:FF:FF`

## 2. 怎么扫

1. 取暂存新增行：`git diff --cached -U0 | grep -E '^\+'`
2. **只排除 `.example`**（`-- . ':(exclude)*.example'`）。**不要排除 `*.md`**——真实 SSID 恰恰是在 README 的示例日志里被发现的。
3. 按 §1 逐条判定，按级别归组。
4. 真实值复现：`git ls-files --others --ignored --exclude-standard | grep -E '(^|/)secrets\.h$'` 找本机的凭据文件，读出宏值再比对。文件不存在就跳过这一步，不要报错。

## 3. 误报与豁免

- 白名单写进 §1.4 或仓库的 pre-commit 钩子，**不做逐个口头豁免**——口头豁免下次就忘了。
- 真实但确实要公开的值（自有域名、公开服务器地址），在审阅里写明理由，用户回复 ① 即视为认可。
- **为了过闸门把值改成占位符后忘记改回来**是更贵的错误：占位符进代码会编译失败或运行时连不上。改就要改到底，并在同一次审阅里说明。

## 4. 与 pre-commit 钩子的分工

钩子是最后一道自动闸门：运行时从 gitignored 的 `secrets.h` 读真实值、扫暂存内容、命中即中止提交。
`§2.5` 是**审阅层的同一件事**，互补关系：

- 钩子挡得住「已知的敏感值」，挡不住「用户自己也没意识到这是隐私」的新类型（新的 IP、新的第三方主机）
- 审阅层负责判断与呈现，钩子负责兜底阻断

两者都不替代 §5。

## 5. 处置优先于重写

已经推送出去的隐私数据，**force push 不等于删除**：远端只是把分支指针挪走，旧提交凭 SHA 仍可访问，直到平台自己 GC（时机不可控）。所以要按下面的顺序想：

1. **轮换凭据**（改密码、换 token、换 key）—— 唯一能真正止损的动作，且成本最低
2. **降低暴露面**：服务前置 CDN、关掉直连端口、仓库转私有
3. **重写历史**：重写 + force push + 请平台清理悬空对象（或删库重建），并接受「所有其他 clone 全部失效」

判断口径很简单：**先问「把这个值轮换掉是不是更省事」**。是，就轮换，历史留着不动。
只有在该值无法轮换（比如它就是拓扑本身，或是对外承诺过的地址）时，才进入第 3 步。
