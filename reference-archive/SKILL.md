# reference-archive：把散落的官方资料固化成可回溯的参考归档

> ⚠️ **触发加载检查**：收到任何「把某块板子/某个开源项目的文档整理下来」「这些参考文档存成 md」「官方更新了，新固件要重新对一下」「帮我核对这块板的引脚对不对」类意图时，**先确认本技能已加载**——若本技能不在当前会话的可用技能列表里（技能快照可能早于本技能安装或更新），先用当前环境的技能加载机制加载它，然后按其流程执行。切忌在未加载技能的情况下直接批量抓取上游站点，或直接采信官方文档表格里的引脚。

定位：与 `research`（一次一问、只产出一份调研结论）、`design-doc-review`（审阅文档本身的质量）、`esp32-firmware-bringup`（本机实测硬件事实）分工——本技能只管**把官方散落资料固化成一份本地可离线查阅、出处可回溯、不确定处显式标注的参考归档**。核心机制是「一手镜像 + 交叉验证 + 不确定项标注」。术语定义见 [`CONTEXT.md`](CONTEXT.md)，实例见 [`references/rlcd-4.2-case.md`](references/rlcd-4.2-case.md)，版本历史见 [`references/version.md`](references/version.md)。

## 1. 何时使用

| 情形 | 动作 |
|---|---|
| 「把这块板的参考文档都存成 md」「官方文档站我要离线能看」 | 走 §3 固化一手资料，再走 §4 核对事实 |
| 「官方更新了，我要用新固件，把旧的重新对一遍」 | 走 §5 增量对账，别全量重做 |
| 「这块板的引脚到底是哪几个」「文档里写的是不是真的」 | 走 §4 交叉验证，逐路取证 |
| 「写一份调研结论就够了」 | 不属于本技能；那用 `research` |
| 「我这块板子焊上不亮、I2C 不应答」 | 不属于本技能；那是本机硬件诊断，用 `esp32-firmware-bringup` |

## 2. 规划归档骨架

### 2.1 定范围与落点

**动作**：先问清三件事再动手——归档对象（哪块板/哪个项目）、落到哪个目录、是否允许把上游内容纳入版本控制。

**判据**：落点有明确回答；上游仓库通常带自己的许可，镜像进本仓库前确认归档目录是被忽略的私有目录，还是允许公开的目录。两者都成立时，**一律优先私有目录**。

**理由**：归档里可能混入上游代码与固件二进制，它们是上游的产出物，混进本仓库的版本历史等于替上游做了分发决定。

### 2.2 目录结构与命名

**动作**：按本节的三层建目录，Markdown 单独成层：归档根放编号 Markdown 与 `README.md` 索引，`assets/` 放本地化图片，`downloads/` 放原样下载的 PDF 与固件，`reference-source/` 放上游仓库的逐字节镜像。

**判据**：每个 `.md` 文件的编号连续、无空洞；`assets/` 与 `downloads/` 里的文件都有出处（哪个页面、哪个 Release）；`reference-source/` 是上游的**逐字节副本**，不含任何本地改动。

**理由**：编号即阅读顺序是离线归档唯一有效的导航手段——离线时没有侧边栏可点。

### 2.3 三类文件的边界

| 类别 | 是什么 | 允许做什么 |
|---|---|---|
| 官方原文存档 | 文档站页面的 Markdown 存档 | 只转写，不改写；保留来源 URL 与抓取时间 |
| 一手资料镜像 | 仓库 tar、固件 bin、数据手册 PDF | 只存不改；附 sha256 与来源链接 |
| 整理文档 | 由多路来源交叉核对后写出的派生结论 | 每条结论标出处；矛盾处显式列出 |

**判据**：三类文件不会互相混装——整理文档里不嵌大段原文，原文存档里不夹带结论。

**理由**：把官方原文和派生结论混在一份文件里，读者无法判断哪句话是官方说的、哪句话是你推断的。这是归档失去可信度的最快方式。决策背景见 [`docs/adr/0001-归档文件分三类且互不混装.md`](docs/adr/0001-归档文件分三类且互不混装.md)。

**细则**：目录职责、编号规则、文件头格式、索引 README 的五块必备内容、固件清单表、镜像体积取舍，见 [`references/archive-layout.md`](references/archive-layout.md)。

## 3. 固化一手资料

### 3.1 文档页转 Markdown

**动作**：用 [`scripts/html-to-markdown.py`](scripts/html-to-markdown.py) 抓取渲染页。站点与页面清单写在一个 JSON 配置里，脚本本身不含任何站点或产品常量。

**判据**：

1. 正文容器定位成功——渲染页的文章容器未必是 `<article>`，配置里的 `article_marker` 命中后按标签配对截取；
2. 表格被还原成 Markdown 表格行，首行自动生成表头分隔；
3. 嵌套列表不重复渲染；
4. `data:` URI 内联图标被替换为文字占位，不落成无效引用；
5. **HTML5 可选结束标签被正确补全**——`<td>` / `<th>` / `<tr>` / `<p>` / `<li>` 常常不闭合，解析器必须自己补，否则整页内容会塌成一坨；
6. 提示块（admonition）的内容**不丢**——警告框的正文必须完整落在引用块里，不能只剩标题。

**理由**：这六类问题在真实文档站上都会遇到，且都表现为「看起来转好了，其实内容丢了」。第 5 条是隐蔽的：HTML5 允许省略结束标签，浏览器会自动补，但 `html.parser` 不会——不手动补，`</td>` 缺失会让整张表格退化成一段连续文字。第 6 条曾经把整段警告说明吞掉，只剩「> **警告**｜版本兼容性说明」一行，读者会以为页面本来就这么短。

**验证方式**：不要只看脚本的退出码。抓完**逐页读一遍生成的 Markdown**，对着原始页面核对段落数、表格行列数、警告块正文——转写脚本的失败几乎都是静默的。

**脚本取舍的决策背景**（为什么只带三个核心、不带 PDF 抽取与位图识别的代码）见 [`docs/adr/0002-自带脚本只保留三个核心.md`](docs/adr/0002-自带脚本只保留三个核心.md)。

### 3.2 图片本地化

**动作**：抓页时同步下载正文图片到 `assets/`，按内容去重，已存在的同名文件不重复下载；Markdown 里的引用改写为相对路径。

**判据**：所有图片引用都是**相对路径**；站点的绝对路径引用一律改写——离线后站点绝对路径会全部失效。抓完后逐张读图确认内容对得上，不能只看文件名。

**理由**：离线归档的图一旦是外链就等于没有；反过来，图片下下来但下错了（裁剪图、占位图、空白图）比没有图更糟。

### 3.3 上游仓库与发布资产镜像

**动作**：仓库用官方 tarball 或 release 源包整包取回，解压后原样存放；固件从 Releases 的资产清单逐个下载，附 sha256。

**判据**：镜像落地后**逐文件 sha1 与源包比对全等**（用 [`scripts/snapshot-diff.py`](scripts/snapshot-diff.py) 跑一遍上游目录与本地目录）；固件二进制头部魔数符合该平台预期（ESP32 镜像为 `e9`），文件大小与 Release 页面标注一致。

**理由**：逐字节校验是「镜像」与「下载了一堆文件」的分界线。整包 tar 比逐文件 API 拉取更快也更可靠——逐个文件 API 拉 2600 个文件既慢又容易静默漏掉。

### 3.4 固件与下载资产清单

**动作**：把官方 Releases 的**全部**资产列成清单：名称、版本、发布时间、来源 URL、本地路径、sha256。

**判据**：清单里包含「用户实际会下载的那几个」与「其余全部」，并标注哪些是例程预编译固件、哪些是整机出厂固件、哪些是第三方适配固件。

**理由**：固件是上游发布节奏最快的东西。用户说「后面要用新的固件」时，他要的是「哪些固件、哪个版本、怎么烧」，不是「代码在哪」。

## 4. 核对硬件事实

### 4.1 来源分级

| 级别 | 来源 | 用途 |
|---|---|---|
| 权威 | 上游 BSP / 驱动源码里的宏与初始化序列 | 引脚、初始化参数的事实源 |
| 佐证 | 官方接口表图、官方第三方框架配置（如 ESPHome YAML）、原理图网表 | 交叉印证 |
| 参考 | 上游 README、示例代码、论坛帖 | 只作线索，不单独成结论 |

**判据**：一条结论至少要有**两个独立来源**支持，且其中至少一个是权威级；只有参考级来源支撑的条目进「不确定项」。

**理由**：官方文档本身也会错。**读图得出的表格和原理图必须反查实物**：接口表里出现过「某器件的列，但板上根本没焊这颗器件」的情况——那列是复用了同一组 I2C 信号的标注，不是板上真有的器件。

### 4.2 多路交叉验证

**动作**：对关键事实（引脚、器件型号、电源分压、初始化序列、分辨率）分别从四条路取证：

1. 官方接口表图（位图，需读图）；
2. 上游 BSP 源码（宏定义、初始化命令序列）；
3. 上游仓库里第三方框架的配置（ESPHome YAML 之类，引脚写成了配置文本，最容易比对）；
4. 外部项目为这块板写的配置（第三方上位机固件的板级配置）。

**判据**：四路取到的数值**逐项一致**才算「已交叉验证」；三路一致记「多数一致」，并在文档里说明第四路为何缺席；两路一致记「双源一致」。

**理由**：四条路的**独立性**是价值所在。官方接口表与官方源码出自同一团队，可能一起错；第三方项目按官方文档抄的，但会漏抄、会按自己板子改，反而能暴露矛盾。

**细则**：四条路各自的取证方法、结论定级、冲突处理顺序，见 [`references/cross-validation.md`](references/cross-validation.md)。

### 4.3 读图与网表提取的坑

**动作**：官方资料里的引脚表常常是**位图**而不是文本。还原它的顺序是：先定位网格线拿到列边界与行边界，再按表头列名把每一格归到正确的列，最后逐格读值。原理图 PDF 的网表同理，但要按「网名 + 引脚标记」的位置关系重建。

**判据**（这些是本次实测踩出来的，通用）：

- PDF 文本层里符号引脚编号与网名**可能错位**——FPC 连接器的具体脚序一旦发现错位，就**不作为事实发布**，只发布信号集合与连接器型号，并注明接插件前需对照原理图复核；
- 抽取出的网表会出现「某个网挂了几十个引脚」的噪声，那是文本顺序问题，不是真实连接；
- 网表噪声不影响结论，但**位图表格的表头错位会直接改变结论**——必须先验证表头对齐再读值。

**理由**：读图与网表是最容易产出「看起来很具体但其实是错的」结论的两条路。宁可少发布一条，也要保住其余结论的可信度。

### 4.4 冲突与不确定项的处理

**动作**：把无法验证、来源互相矛盾、或只能靠推断的条目集中列成「不确定项」小节，写明**冲突在哪两方**、**为什么无法判定**、**判定需要什么条件**。

**判据**：

1. 板上有、上游文档和代码里都找不到对应实现的硬件（如丝印标注清楚的拨码开关），**不写进事实表**，只记在不确定项里说明「官方无对应实现」；
2. 官方文档本身就缺链接的（原文即 `****`），按原样保留并注明「原页面即如此」，不补猜测链接；
3. 官方例程之间参数不一致的（如同一块板一处写横屏 400×300、另一处写竖屏 300×400），**两个都记并注明差异**，不替官方选一个。

**理由**：不确定项是归档里最值钱的部分。读者知道哪里能信、哪里不能信，这份归档才敢用；一份「什么都有结论」的归档，反而让人在踩坑时怀疑整份文档。

## 5. 官方更新后的增量对账

### 5.1 对账三张表

**动作**：拉上游最新的树快照，与本地镜像跑 [`scripts/snapshot-diff.py`](scripts/snapshot-diff.py)，得到三张表：**上游有本地无**（新增）、**本地有上游无**（删除）、**两边都有但 sha1 不同**（内容变更）。sha1 相同的文件计入「确认无变化」。

**判据**：三张表全部产出，而不是只报一个「有 N 个文件变了」的总数。总数无法区分「改了一行注释」和「换了整个驱动」。

### 5.2 认出「改名未改码」

**动作**：删除表里的文件，先去新增表里找同名同 sha1 的文件。找到了就是**目录改名或搬家，代码一个字节没动**。

**判据**：本次实测遇到过上游把一个 255 文件的目录整体改名、其中 253 个文件 sha1 完全一致、只有两个 README 变了的情况。遇到这类改名，**只更新文档里提到路径的部分**，不重写任何技术结论。

**理由**：这是增量对账最容易误判的一类。全量重建时它看起来像「大改」，人会顺手把结论也一起改掉——而实际上技术内容根本没变。

### 5.3 决定要更新哪些文档

**动作**：把对账结果映射回整理文档：三张表里出现的事实是否在文档中被引用？被引用的才需要改，且改动范围严格限定在该事实。

**判据**：每一处文档改动都能指回对账表里的具体条目；没有对账依据的改动一律不做。文档里**不写「官方改了什么」的流水账**——那属于版本记录，写进 [`references/version.md`](references/version.md) 的对应条目或归档的版本小节。

**理由**：流水账会随每次更新膨胀，把归档变成变更日志，而读者要的是「现在的事实是什么」。

## 6. 归档自检

**动作**：交付前跑完四项自检。

| 自检项 | 怎么查 | 通过标准 |
|---|---|---|
| 内部链接自洽 | 用 [`scripts/check-links.py`](scripts/check-links.py) 查归档目录 | 缺失引用 0、未引用资源 0 |
| 一手镜像完整 | [`scripts/snapshot-diff.py`](scripts/snapshot-diff.py) 比对上游与本地 | 逐文件 sha1 全等 |
| 固件完整 | 对 Release 清单逐个算 sha256 | 与清单记载一致 |
| 结论可回溯 | 抽查整理文档里的每条结论 | 能指回具体来源（文件 + 行 / 图 + 位置） |

**判据**：四项全过；任何一项不过就把对应条目移到不确定项，而不是删掉检查。

**注意**：镜像了上游源码树时，**链接检查默认只查顶层 `.md`**——上游第三方 README 里的相对链接指向上游仓库内部路径，在本地并不成立，误报会淹没真问题。需要连嵌套目录一起查时显式开递归模式。

**理由**：自检的价值不在于发现错误，而在于证明「这份归档里没有你不知道的东西」。四项分别覆盖了引用、完整性、字节一致性与结论可回溯这四种失效模式。

**脚本的用途、参数与已知局限见 [`references/scripts.md`](references/scripts.md)。**

## 7. 安全边界（硬性，任何路径下均适用）

1. **不擅自 commit / push**——归档目录多半被忽略，本就没有提交的意义；即便不在忽略列表里，提交与推送都要用户明确许可。
2. **凭据与私有信息零入库**——脚本、配置与 reference 里不得出现 token、私钥、内网地址、带用户名的路径。本技能会批量读取上游资源，脚本里极易顺手留下本机绝对路径；入库前必须逐文件清掉。
3. **中文与二进制文件不用 PowerShell 读写**——PowerShell 管道按 GBK 解码外部输出，UTF-8 中文会乱码；带 BOM 与 CRLF 的转换会把文件改坏。用脚本按 UTF-8 无 BOM、LF 写回，或用能指定编码的工具。
4. **抓取要节制**——只发 GET、只抓公开资源、请求之间留间隔（默认 1 秒）、不镜像与归档目标无关的大文件。镜像几百 MB 的上游仓库对一个公开站点是骚扰，不是采集。
5. **不臆造缺失事实**——官方没给的链接、没列的器件、没写明的脚序，宁可留空并记入不确定项，也不填一个看起来合理的值。

## 8. 完成后报告

改动完成后一次性向用户报告：

1. **归档位置与结构**——目录树 + 三类文件各有多少；
2. **文档清单**——每个 `.md` 一句话说明它装了什么；
3. **自检结果**——四项自检各自的通过情况与数字；
4. **不确定项**——逐条列出：结论是什么、冲突在哪两方、判定需要什么条件；
5. **未做的事**——本次故意没做的（例如未提交、未镜像某类大文件）与建议下一步。
