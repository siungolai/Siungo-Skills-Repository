# commit-report：审阅门式 Git 提交

> ⚠️ **触发加载检查**：收到任何「提交 / commit / 推送 / push / 先看看改了什么再提交」类意图时，**先确认本技能已加载**——若本技能不在当前会话可用技能列表（技能快照可能早于本技能安装/更新），先执行 `skills_list` 查证、再用 `skill_view(name='commit-report')` 加载，然后按其流程执行。切忌在未加载技能的情况下直接提交。

定位：与内置 /commit 命令互补——本技能以**强制审阅门**为核心，用户看到变更总揽与 commit 信息全文并明确确认后，才执行提交。**push 默认不执行**，仅在用户明确选择时进行。

## 一、目标仓库定位与前置自检

1. **确定目标仓库**：当前目录为 git 仓库则直接采用；否则向用户列出候选或请求指定仓库路径／URL，选定后继续流程；用户拒绝指定时终止。
2. 空仓库（无任何提交历史）：跳过"匹配既有风格"，按通用规范生成首次提交信息，并在审阅中注明"首次提交，无历史风格可匹配"。
3. **状态快照（场景路由前置）**：读取三要素并输出——
   - 分支名与上游（`git rev-parse --abbrev-ref --symbolic-full-name @{u}`）；
   - **本地领先上游的未推送提交数**（`git rev-list --count @{u}..HEAD`，无上游记 0）；
   - 工作区与暂存区变更（含未跟踪文件）。
   按快照路由到两种场景：
   - **场景 A（默认）**：本地无领先提交，仅有未提交工作区变更 → 按第二节常规流程创建新提交；
   - **场景 B（领先提交）**：本地存在 ≥1 个未推送提交（可有/无工作区变更）→ 按第三节「两区模板」审阅：先审已存在待推送提交（内容既定、文案不可改除非用户要求重写历史），再审本次待创建提交（若有工作区变更）。
4. **无事可提交**（工作区与暂存区均干净、无未跟踪文件、且无领先提交）：报告"无事可提交"，结束，不进入审阅。
5. detached HEAD 状态：提示先切换或新建分支，不执行任何操作。

## 二、分析阶段（场景 A：创建新提交）

1. **风格匹配**：读取最近 10 条提交的主题行，归纳并输出三要素——前缀风格、语言、主题行模板（如 `Add <skill> skill`、`docs: <主题>`）；本次匹配到的模板须在审阅中注明。无明确风格可循时，默认 conventional commits、简体中文。
2. **变更盘点**：按三组分类——已暂存／未暂存／未跟踪；同一文件同时存在已暂存与未暂存变更时合并为一行，状态标注"部分暂存"。
3. **改动摘要**：变更类型枚举为新增／修改／删除／重命名四类，每文件一行（类型＋核心内容），规则：
   - 单文件 diff 超过 300 行：只读头部与 `diff --stat`，标注"大改动（概要）"；
   - 二进制文件：标注"二进制文件（大小 X）"；
   - 未跟踪新文件：读文件头部判断性质后写摘要；
   - 变更文件总数超过 20 个：低重要性文件按目录聚合为一行并附统计（如"src/ 下 32 个文件，+512 -96"），重要文件（配置、入口、依赖清单等）仍单独列出。
4. **生成 commit 信息草案**：按匹配风格书写主题行＋正文（HEREDOC 格式），正文按需列要点。

## 三、审阅展示（两区模板；场景 A 仅展示第 2 区）

### 第 1 区：已存在待推送提交（场景 B）

| # | 提交（短 SHA） | 主题 | 时间 | 文件统计 |
|---|---|---|---|---|
| 1 | `abc1234` | `<主题行>` | `<提交时间>` | +N / -M，K 文件 |

逐条附注：此区提交**文案既定**——修改需用户明确要求（重写历史，见第六节 §6.4）；审阅聚焦"内容是否认可 + 是否一并推送"。

### 第 2 区：本次待创建提交（场景 A / AB）

1. **仓库与分支**：仓库标识（路径或 owner/repo）、分支名、与上游关系；
2. **commit 信息全文**（草案）：主题行＋正文，风格与既有提交一致；
3. **变更总揽表**（三组分组，部分暂存合并呈现）：

   | 状态 | 文件 | 改动摘要 |
   |---|---|---|

4. **风险预警**（敏感文件加粗、大文件标注，如有）；
5. **回应路径**（固定文案）：

```
请回复：
① 确认提交（仅 commit，不 push）
② 确认提交并 push（推送至当前分支上游）
③ 需要调整（改 commit 文案 / 剔除文件 / 其他）
```

> 场景 B 说明：本地已有未推送提交时，回复② 推送的是**全部领先提交链**（git push 是链式的，无法只推部分）；若只想推送其中一部分，请回复③ 并说明，将评估重写历史方案（风险见第六节 §6.4）。

## 四、回应判定

- **确认判定（操作性定义）**：凡包含提交意向且不含任何修改意见的明确指令，均视为确认——如"确认提交""全部提交并推送""直接提交"等；上文枚举仅作示例。纯模糊应答（如单独一个"嗯"）不构成确认，需重新征询。
- **回复①** → 按确认范围执行 `git add`（默认全量变更；用户点名剔除的文件排除在外）→ `git commit`（HEREDOC 格式书写提交信息）。
- **回复②** → 同上执行 commit（场景 A），随后 push 至当前分支上游；场景 B 且无新工作区变更时跳过 commit 直接 push 领先提交链；当前分支无上游时，先追加确认是否执行 `git push -u origin <分支名>`，确认后才执行。
- **回复③** → 按反馈修订（commit 文案或提交范围），重新完整展示审阅；修订循环次数不限，由用户主导。
- **用户发起时明说"跳过审阅直接提交"** → 不展示直接执行（当次显式指令优先），但第五、六节仍然全部适用。

## 五、执行通道与降级

1. **默认通道**：本地 git 命令行（add → commit → push）。
2. **网络探测（push 前快速判定，避免长时间挂起）**：
   - `curl -s -o /dev/null -w '%{http_code}' --connect-timeout 5 https://github.com/`（github.com:443）
   - `curl -s -o /dev/null -w '%{http_code}' --connect-timeout 5 https://api.github.com/`
   - 两者皆通 → 默认通道直接 push；github.com 不通但 api.github.com 通 → 直接走降级通道（gh api），不必先等 git 超时；两者皆不通 → 报告网络阻塞，不重试、不自动切换其他网络。
3. **降级通道**：git 传输故障（HTTP2 framing 错误、CONNECT 5xx、连接超时、Empty reply 等，或探测判定直连不可达但 api 可达）时，改用 **`scripts/push-via-api.py`**（随本技能分发的通用脚本：解析远端仓库 → 按序重建领先提交链 → 更新 ref），或按四步手动：`git/blobs`（base64 编码）→ `git/trees`（携带 base_tree 或全量条目）→ `git/commits`（message + tree + parents[]）→ `PATCH git/refs/heads/<分支>`。
   - 两个已知陷阱：MCP github 连接多为集成令牌，写入常返回 403（not accessible by integration），写操作一律用 gh CLI；`gh api` 布尔字段必须用 `-F`（`-f` 会把 false 当字符串导致 422）。
   - **中文/空格路径陷阱**：文件名含中文或空格时，`git diff --name-only` 输出被引号包裹且转义——用 `-z`（NUL 分隔）读取路径列表；blob content 用 base64 编码上传。
   - **SHA 一致性校验（降级成功的判定标准）**：重建 tree 的返回 sha 必须等于本地 `git rev-parse <commit>^{tree}`；重建 commit 的返回 sha 必须等于本地 commit sha（author/committer 时间用 ISO 8601、`%aI`/`%cI` 格式，逐字段原样重建）；ref 更新后远端 sha == 本地 HEAD。全部一致才报告推送成功。
   - **本地 tracking ref 同步**：git 直连不通时 `git fetch` 同样失败，降级推送成功后需手动 `git update-ref refs/remotes/origin/<分支> <新sha>`，否则本地 `git status` 仍显示领先（假象）。
4. **降级约束**：降级只改变传输手段，不改变审阅确认过的内容——仍为同一批提交、同一 message、同一文件范围；ref 更新 force=false。
5. **空范围防护**：执行前校验确认范围非空；剔除后为空则报告并回到审阅，不产生空提交。

## 六、安全边界（硬性，任何路径下均适用）

1. 禁用 `--no-verify`；pre-commit 钩子失败时报告原因并停止，不绕过。
2. 禁止 force push；禁止 amend 已推送的提交。
3. push 被远端拒绝（non-fast-forward）或网络失败：只报告差异与建议（如先 pull），不自动 pull／rebase／重试。
4. 不擅自新增或删除文件，不改动用户未确认范围之外的内容。
5. commit 信息语言跟随仓库既有风格；无历史可参考时使用简体中文。
6. **场景 B 历史提交的改写**：已存在待推送提交（未推送）需要改文案/合并/拆分时，属重写历史操作——须用户明确要求，说明影响（提交 sha 改变、工作区需协调）并给出方案（如 `git reset --soft` 到上游后重新提交，或 `git rebase -i`），经用户确认方案后才执行；绝不擅自 amend/reset/rebase。

## 七、完成后报告

提交（及推送）完成后，向用户报告：

1. **commit 哈希**（完整 SHA）、主题行、作者、时间；场景 B 逐条列出已推送提交（SHA + 主题 + 文件统计）；
2. **变更统计**：files changed / insertions / deletions；
3. **推送验证**（若执行 push）：远端分支最新提交 SHA 与本地一致；降级通道报告 tree/commit/ref 三重 SHA 校验结果；有条件时附关键文件 blob SHA 比对结果；
4. **执行通道说明**（git 或降级通道），供追溯。
