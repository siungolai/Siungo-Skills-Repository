# esp32-firmware-bringup：ESP32 固件 bringup 与硬件诊断

> ⚠️ **触发加载检查**：收到任何「给这块板子做 bringup / 接了个新屏或新传感器 / I2C 器件没应答 / 节拍跑偏了 / 写个 ESP32 固件」类意图时，**先确认本技能已加载**——若本技能不在当前会话的可用技能列表里（技能快照可能早于本技能安装或更新），先用当前环境的技能加载机制加载它，然后按其流程执行。切忌在未加载技能的情况下直接按规格书参数写固件。

定位：与 `skill-authoring`（怎么写技能）、`design-doc-review`（怎么审文档）分工——本技能只管**把规格书上的 ESP32 硬件参数变成本机实测事实，并把新器件从接线推进到长跑**。核心机制是「bringup 优先」：硬件链路没在本机跑通之前，不写依赖它的上层代码。版本历史见 [`references/version.md`](references/version.md)。

## 1. 何时使用

| 情形 | 动作 |
|---|---|
| 「给这块板子 / 这个新器件做 bringup」「接了个新屏 / 新传感器 / 多路复用器，先跑通再写功能」 | 走 §2 全流程 |
| 「I2C 器件没应答」「扫不到地址」「屏不亮」 | 走 §5 诊断阶梯，**先物理层后固件** |
| 「节拍跑偏了」「掉个外设刷新就卡」 | 走 §2.4.2 离线保护 + §4 非阻塞范式 |
| 「DHT11 / SSD1306 / PCA9548A / 1602 怎么接怎么驱动」 | 先读 §2.4.3 器件专项路由表里的 reference |
| 「帮我写个 ESP32 上位机」「这块板子用什么库」 | 不属于本技能；本技能只覆盖已在本机实测过的器件与接线 |

## 2. 标准流程

六个阶段串行推进，前一阶段的判据不满足不进下一阶段。跳过 bringup 去写上层代码，是本文档要防的主要失败模式。

### 2.1 需求冻结

**动作**：把需求写成可核对的清单，每条需求项必须能映射到一个常量或一个外设。

**判据**：清单里没有「顺便也看一下」这类模糊项；每条都能回答「它对应哪个 GPIO / 哪个地址 / 哪个节拍常量」。需求含糊时停下来问，不要替用户假设。

### 2.2 硬件事实采集

**动作**：记录本机实测读数，而不是规格书参数。

**判据**：以下各项都有**实测记录**（万用表读数 / `i2c-scan` 输出 / 串口日志），不是「手册上说」：

- 板子型号、revision、Flash/PSRAM 容量、端口号（见 [`references/hardware-facts.md`](references/hardware-facts.md)）；
- 每个用到的 GPIO：实测通断与静态电平，不是规划值；
- 每个总线器件的实测地址（丝印地址含读写位，别直接当 7 位地址用）；
- 上拉归属：上游谁提供、下游谁提供，两侧分别确认。

**未实测的一律标「待 bringup 验证」**，不写成可用。

### 2.3 bringup 阻塞前置

**动作**：先写一个最小验证项目，只证明这条链路真的通。硬件通了再写功能。

**判据**（三条同时满足）：

1. 期望的地址确实应答（`i2c-scan` 有输出，不是「应该会」）；
2. 多个同址器件时，单独操作其中一个不干扰其余（同内容显示无法区分是否真的切换成功，必须显示不同内容）；
3. 拔掉任意外设后，节拍仍按原速跳（见 §2.4.2）。

**理由**：硬件风险与软件风险的验证成本差异极大——硬件只能实物验证，且拓扑假设一旦错误（地址不对、上拉位置不对、器件其实是另一类），推翻的是整个上层架构。bringup 产出的驱动、探测逻辑、诊断输出全部是后续项目的直接依赖，不是一次性丢弃的代码。

### 2.4 节拍与驱动实现

#### 2.4.1 非阻塞范式

- `millis()` 单调计数：深睡停走、约 49.7 天回绕，用无符号减法天然兼容；
- `now - last >= PERIOD` 且 `last += PERIOD` **累加推进**，不写 `last = now`——后者会累积漂移；
- 每轮 `loop()` 只读一次 `millis()`，多处读会互相错位。

#### 2.4.2 离线保护（不可跳过）

**动作**：探测失败后，刷新函数直接返回，不发任何总线事务。

**判据**：从机不在线时，节拍实测仍精确。参考值：屏缺席时 45 tick / 45 秒 = 1.0000 tick 每秒，无漂移。

**理由**：`Wire.setTimeOut(50)` 下，一轮 SSD1306 刷新 8 页 × 2 次事务 ≈ 800ms 阻塞，足以把 1 秒节拍带偏。计时精度必须与从机在线状态解耦。

### 2.5 验收与长跑

**判据**（逐条实测，不是估算）：

1. 帧率实测达到设计值（如 1.0000 帧/秒），不是「看起来差不多」；
2. 拔掉任意外设，节拍漂移 < 1 帧/分钟；
3. 资源留 20% 余量（RAM/Flash 口径见 [`references/hardware-facts.md`](references/hardware-facts.md) §5）；
4. 长跑 ≥ 2 小时无复位、无内存泄漏；
5. 刷新计数 `#N` 持续递增——这是「刷新周期真在跑」的现场证据。

**台架压缩**：周期太长时用 `TIME_SCALE` 按比例缩短，在台架上快速验完多种周期；**验完必须复位为 1**，否则带着压缩比例进长跑，验收数字全是假的。

### 2.6 流程总表

| 阶段 | 核心动作 | 通过判据 |
|---|---|---|
| 需求冻结 | 需求映射到常量/外设 | 无模糊项 |
| 硬件事实采集 | 记录实测读数 | 无「规格书上说」 |
| bringup 前置 | 最小验证项目 | 地址应答 + 单路不互扰 + 拔外设节拍不漂移 |
| 节拍与驱动 | 非阻塞 + 离线保护 | 从机缺席仍 1.0000 tick/秒 |
| 验收长跑 | 逐条实测 | 帧率 + 漂移 + 余量 + 2 小时 |

## 4. 非阻塞时序与节拍解耦

完整范式见 §2.4.1，这里是三条最容易写错的：

1. **`last += PERIOD` 不写 `last = now`**——后者每轮漏掉的时间差会累积，一小时能漂出秒级；
2. **`millis()` 每轮只读一次**——循环里多处采样，各处的「现在」不是同一个现在；
3. **无符号减法比较 `now - last >= PERIOD`**——天然兼容约 49.7 天回绕，不需要写绕回判断。

## 5. 诊断优先：先物理层后固件

**顺序即纪律**：通断确认之前，地址扫描与日志全是无效劳动。

| 层 | 判什么 | 通过标准 |
|---|---|---|
| 1 电源真值 | 供电真的到了器件 | 万用表读数符合，不是「灯亮」 |
| 2 万用表通断 | 信号真接到了器件 | 排针对应针导通，无虚接 |
| 3 总线静态电平 | 上拉在线 | `pullup=HIGH` |
| 4 地址扫描 | 器件在这个地址 | 期望地址有应答 |
| 5 错误码判读 | 卡在哪一层 | 见下 |
| 6 固件 | 前面都过了才看 | 串口日志 + 逻辑 |

**错误码**：`2` = 该地址无应答（查器件供电/焊接/跳线）；`5` = 总线超时（**停止查地址，直接查物理层接线**）。判错码 = 白干。

**判读会骗人**（真实教训）：1602 背包模块曾呈现「背光亮 + 两线 HIGH + 全段无应答」，收敛到「模块硬件故障」。反证是把背包整块拔下，**背光仍亮、两线仍 HIGH**——背光由背包上 PCF8574 的 P7 驱动，器件真拔掉不可能还亮。真相是排针没插到底或 16 针并口虚接。**「背光亮 = 供电到位」不成立**，所以通断排在仪器判读之前。

诊断工具台、七个工具的用法与日志判读约定见 [`references/diagnostic-tools.md`](references/diagnostic-tools.md)。

## 6. 日志可观测与凭据约定

- 串口日志用 ASCII 不用中文（UTF-8 到部分串口工具乱码，而故障时这是唯一线索）；
- 无效读数写 `--` 不写 0（0°C 是合法读数，写 0 就跟没读到混在一起）；
- 刷新计数 `#N` 作为「1 秒更新一次」的现场证据；LCD 掉电后画面保留，静止的字不能证明刷新在跑；
- 定长覆盖：每行补空格到满列防残影；
- 两类串口行分开：节拍行（每次刷新）与采样行（每次采样，固定字段 CSV），`grep -c 'ok=1'` 统计成功率；
- 诊断工具放 `tools/` 独立 platformio 工程（同一 `src/` 两个 `setup()`/`loop()` 链接失败）；
- 凭据写 `**/src/secrets.h` 并 gitignore（`**/` 前缀必须有，否则被锚定到仓库根等于没忽略），只留 `secrets.h.example`。

## 7. 安全边界（硬性，任何路径下均适用）

1. **先接线后上电**——S3 IO 是 3.3V，直短 GND/3V3 烧 IO。
2. **5V 器件的 SDA/SCL 先量再连**——1602 背包接 5V 时上拉把总线拉到 5V，ESP32-S3 IO 非 5V 耐受（绝对最大 VDD+0.3V ≈ 3.6V），直连经 ESD 二极管灌电流慢性损坏引脚，不当场冒烟；上电前用万用表量背包 SDA/SCL 对 GND 空闲电压，应等于转换模块 LV 侧 3.3V，量到 5V 先别连。跑一阵 IO 失灵/发热 = 立即断电。
3. **不重复加上拉**——上下游模块通常已自带，再补 4.7k 会把等效阻值压到逼近从机 sink 极限（SSD1306 ≈ 3mA）。
4. **不占用 GPIO19/20、不在 GPIO1/2 上接 I2C**——前者失去 USB 串口，后者实测全段超时。
5. **不改已实测可用的接线与地址**——本文件记录的是实测事实，改动前重新走 §5 诊断阶梯。
6. **台架压缩比例验完必须复位为 1**——带着 `TIME_SCALE` 进长跑，验收数字是假的。
7. **未实测的器件状态标「待 bringup 验证」**——把规格书参数写成实测，会让读者误以为验证过。

## 8. 完成后报告

1. **bringup 判据逐条对照**：地址应答 / 单路不互扰 / 拔外设节拍不漂移，各给出实测读数；
2. **帧率与漂移实测值**（如 1.0000 tick/秒、45 tick/45 秒），以及长跑时长；
3. **资源占用**：RAM/Flash 实测值与余量（口径见 hardware-facts §5）；
4. **未解决项**：仍标「待 bringup 验证」的器件与原因；
5. **诊断结论**：若走过 §5 阶梯，说明最终卡在哪一层、判据是什么；
6. **凭据状态**：确认 `secrets.h` 未入库、只留 `.example`。
