# deploy-report：审阅门式部署上线

> ⚠️ **触发加载检查**：收到任何「部署 / 上线 / 发布 / 更新线上 / 回滚」类意图时，**先确认本技能已加载**——若本技能不在当前会话可用技能列表（技能快照可能早于本技能安装/更新），先执行 `skills_list` 查证、再用 `skill_view(name='deploy-report')` 加载，然后按其流程执行。切忌在未加载技能的情况下直接动服务器。

定位：与 commit-report 互补——commit-report 管「变更进入仓库」，本技能管「变更进入线上」。核心是**强制审阅门**：用户看到部署方案全文（变更总揽、执行步骤、备份与回滚路径、验证计划）并明确确认后，才执行上线；失败时停下报告、绝不自动回滚。

## 一、目标定位与前置自检

1. **确定目标项目与部署档案（profile）**：读取项目根目录的部署档案（约定文件名 `deploy-profile.md`，可另存为 `.deploy-profile.md` 等私有命名，字段模板见 `references/deploy-profile.template.md`）。
   - 档案存在且字段齐全 → 按其执行；
   - 档案存在但缺字段 → 向用户请求缺失字段（会话内临时提供亦可，见场景 B）；
   - 档案不存在 → 场景 B。
2. **状态快照**（读取三要素）：
   - 部署物状态：构建产物是否存在、源码是否有变更；
   - git 基线（如有）：档案记录的上次部署标识（commit sha 或产物时间戳）与本地 HEAD 的关系；无记录记 0；
   - 工作区变更：未提交的源码/配置变更。
   按快照路由场景。
3. **场景 A（默认）**：档案齐全 + 有明确部署物 → 进入 §2 分析、§3 审阅。
4. **无事可部署**：本地与线上基线一致、无新部署物、无任何变更 → 报告"无事可部署"，结束，不进入审阅。
5. **场景 B（档案缺失/不全）**：缺失字段由用户在会话内提供，本次按会话参数执行，并在完成后报告中注明"临时参数未入档，建议补齐档案"；若确认该项目将反复部署，先按模板建档再继续。
6. **git 仓库含未提交变更时**：提示可先走 commit-report 提交门；用户明确选择"按当前工作区状态部署"则纳入本次范围，但审阅中必须显著标注**「包含未提交变更」**。

## 二、分析阶段

1. **变更盘点（双轨）**：
   - **有 git**：盘点上次部署标识以来的提交链（逐条主题行 + 文件统计）与未提交变更。规则：单文件 diff 超过 300 行只读头部与 `diff --stat`，标注"大改动（概要）"；二进制文件标注大小；变更文件总数超过 20 个时按目录聚合（重要文件：配置、入口、依赖清单、迁移脚本仍单独列出）。
   - **无 git（全量发布模式）**：按部署物构成盘点——前端构建产物（目录/文件数/体积）、后端源码或二进制、数据与配置类文件；如有项目部署记录文档（里程碑/交接文档），引用其记录的线上基线。
   - **三类必检项**（无论双轨，须在审阅中显式列出或声明无）：依赖清单变更（package.json / go.mod / 各类 lock）；配置变更（新增配置项、端点、密钥引用）；**破坏性变更**（数据库结构、文件路径、API 路由、删除旧文件、前端路由与后端接口不兼容）。
2. **技术前置核验（agent 自查，不问用户）**：
   - 构建平台差异：本地产物是否与服务器兼容（Windows 构建的二进制不可直接用于 Linux 服务器；CGO/动态链接类程序须在服务器构建或交叉编译，静态资源无此问题）；
   - 传输与覆盖风险：目标是否为运行中文件/占用目录、权限属主是否匹配（systemd 强隔离服务只写 ReadWritePaths 内的路径）；
   - 数据库类文件是否会被本次操作触碰：活动数据库绝不覆盖（详见 §8.5）。
3. **起草部署方案草案**：步骤序列（构建 → 备份 → 传输 → 原子替换 → 重启/重载 → 验收），每步给出命令草案或通道描述；**备份与回滚路径**（备份位置、命名规则、保留份数、回滚 = 恢复最近备份 + 重启 + 基础验收）；**验证计划**（档位 + 清单，见 §5）；风险预警与耗时预估。

## 三、审阅展示（部署方案；展示后停下等待）

1. **目标与基线**：项目标识、服务器（仅档案中的公开标识，不展示任何凭据）、当前线上版本标识、本次部署物版本标识（commit sha 或产物校验和 + 时间戳）；
2. **变更总揽表**：按 §2.1 盘点结果组织（提交链 / 文件分组 / 破坏性变更高亮）；
3. **部署步骤命令序列**：完整列出每一步实质动作（备份、上传、替换、重启、验收）与执行通道；
4. **备份与回滚路径**：备份落点、保留份数、回滚的精确执行方式；
5. **验证计划**：档位（默认 T2 冒烟）+ 清单条数；变更面大时明确建议是否升级 T3 回归（T3 必须用户批准才执行）；
6. **风险预警**（如有）：破坏性变更、需写生产数据的冒烟用例、耗时操作、外部依赖；
7. **回应路径**（固定文案）：

```
请回复：
① 确认部署（严格按方案执行，范围外不做任何操作）
② 需要调整（改步骤 / 剔除内容 / 换验证档位 / 其他）
③ 取消本次部署
```

## 四、执行阶段（仅在用户回复①后）

1. **构建与本地自检**（如方案含本地构建）：执行构建命令；本地测试（如有）；记录产物 sha256 供远端核对；构建环境踩坑参考 `references/pitfalls-and-patterns.md` §环境怪癖。
2. **服务器备份（先备份后动刀，备份失败即停）**：将现役部署按方案备份至档案指定目录，命名 `<app>-<描述>-<yyyyMMdd-HHmmss>`（时间戳值须预生成后传递，避免外层 shell 解析问题）；清理超过保留份数（档案 retention，默认 3）的最旧备份。数据目录/数据库按档案规则单独备份（活动文件只做副本，绝不原地覆盖）。
3. **传输到临时路径**：上传至远端临时位置（如 `/tmp/` 或目标旁的 staging 名），**绝不直接覆盖现役文件**；传输完成按需核对校验和（与本地 sha256 比对）。
4. **原子替换**：
   - 运行中二进制/服务文件：先 `mv` 现役文件至备份名（§4.2 已备），再 `mv` 新文件至现役路径；**禁止 `cp` 直接覆盖运行中文件**（Text file busy / 非原子）；
   - 静态目录（前端产物）：解压/同步至新位置后切换引用，或按既有约定解压覆盖（注意 nginx root 指向）；
   - 权限与属主与现役一致（强隔离服务注意服务账号属主，如 www-data）。
5. **重启/重载**：`systemctl restart <服务>` 或 `nginx -t` 通过后重载；随后核验进程存活（is-active）、监听端口、**启动后日志无新增错误**（进程在 ≠ 正常，必须看日志）。
6. 任一步失败 → 立即停止，转 §6。

## 五、验收阶段（三档内建）

- **T1 基础**：目标可达（端口/域名解析）+ HTTP 状态码 + 关键响应头。
- **T2 冒烟（默认）**：基础之上，按档案 smoke 清单逐条请求关键页面/API 路径并断言期望状态码；关键产物 MIME/缓存头；服务日志无新增错误。含异步任务的项目须等到任务**完成态**（如批量重建类任务轮询到全部成功），不能只看提交请求返回 2xx。
- **T3 回归（仅用户批准后执行）**：按项目验收清单跑业务用例，编号逐条记录结果（如 "22/22" 风格），可含浏览器截图留证。
- 验收逐条编号记录；T1/T2 失败 → 转 §6；T3 出现阻断项 → 转 §6。

## 六、失败处理与回滚

1. 执行或验收任一步失败：**立即停止**，报告三要素——① 失败步骤与证据（命令输出/状态码/日志摘录）；② 可能原因判断（含"验证方法误报"的可能，如缓存、路由前缀、工具通道限制）；③ **精确回滚命令**（基于 §3 已展示的备份路径）。
2. **绝不自动回滚、不自动无界重试**：是否回滚、何时回滚由用户决定；单次重试同一命令需说明理由并经用户同意。
3. 用户批准回滚 → 按 §3 展示过的回滚路径执行（恢复最近备份 → 重启/重载 → T1 基础验收）→ 报告结果；用户要求调整方案后重试 → 修订后**重新走 §3 审阅**（变更过的方案须再次确认）。

## 七、完成后报告

1. 上线时间与版本标识（commit sha 或产物校验和 + 时间戳）；
2. 执行摘要：备份落点与保留数、替换方式、服务重载结果；
3. 验收结果逐条（档位 + 通过数/总数，失败项明细）；
4. 回滚备忘：当前可回滚的备份标识与命令（留存回滚窗口）；
5. 遗留事项：临时文件清理情况、未入档参数、下次部署前需更新的档案字段。

## 八、安全边界（硬性，任何路径下均适用）

1. **凭据零入库**：本技能产出或修改的任何将提交/分发的文件（SKILL.md / references / scripts）不得含任何密钥与凭据——SSH key、密码、token、私钥、监控 key、cookie、连接串中的口令等一律禁止。敏感信息只允许存在于：会话内、环境变量、项目内 **gitignore 的私有文件**（含部署档案实例）。发布/提交前必须执行 `references/publish-check.md` 自检。
2. 未经用户明确确认不执行：部署、回滚、重启服务、删除或覆盖服务器文件、清理远端备份。
3. 只在已批准方案范围内操作：不顺手"修别的"、不清理无关文件、不临时加做未展示的步骤。
4. 禁止直接覆盖运行中文件、禁止无备份的破坏性操作、禁止在服务器遗留测试数据或敏感文件（测试后即清理，清理动作须在报告中交代）。
5. 活动数据库文件不覆盖、不原地改写；涉及数据库迁移必须先备份并展示迁移影响面。
6. 与本机沙箱/工具限制冲突时不绕行：本地工具受限（如 HTTPS 验证通道受限）按档案采用替代验证通道；需提权/需用户手动执行的操作交由用户执行或批准。
7. 网络故障或远端拒绝：只报告差异与建议，不自动重试轰炸。
