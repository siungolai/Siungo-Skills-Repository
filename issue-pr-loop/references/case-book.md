# 实测基线与反例（case-book）

> 2026-11-08 的一份公开协作实录（wiredraw 仓库）里，一个单人 + 多个 agent 会话在 5 天内跑出了下面这些数字。本仓库的 `SKILL.md` 就是从这套流程提炼的。**读法**：数字只作量级参考，不作目标；反例才是可以直接拿来对照的部分。

---

## 1. 量级基线

| 指标 | 实测值 |
|---|---|
| 建仓起算 | 5 天（2026-11-04 → 11-08） |
| 提交总数 | 502 次，单日峰值 224 次 |
| 同期产出 | 144 个 issue、153 个 PR，其中 **151 个 PR 已合并**（几乎每个 PR 都合了） |
| 同时存活的 PR 上限 | 10 |
| 合并间隔中位数 | 15.1 分钟 |
| 单小时合并峰值 | 9 次 |
| 每日提交曲线 | 11-04 15 次 → 11-05 49 次 → 11-06 162 次 → 11-07 224 次 → 11-08 52 次（回落） |

同一个作者在四个仓库用同一套流程：IdleJot（195 issue / 205 PR，主分支 `slim`）、gallery-culling（42 / 55，`master`）、dilink-auto-android（28 / 29，`main`）、wiredraw（144 / 153，`main`）。四个仓库的文档几乎同名，**换仓库只换目录名**——这是 `SKILL.md` §13 记忆外置的直接证据。

**PR 数量的量级才是重点**：153 个 PR 对应 502 次提交，平均每 3.3 次提交一张 PR。也就是说那 502 次提交里没有一次是直接落到主干的——每一次都经过了「分支 → PR → 门禁 → 评审 → 排队合并」。这组数字本身就是「PR 是唯一入口」在真实项目里跑得动、而且跑得快的证据。

## 2. 四个反例（本技能要防的失败模式）

1. **开单边想边写**：单子写到一半发现验收要跑两轮真机，于是正文越长越乱。正确做法是按 `flow.md` 的「拆分信号」先拆、再集中成单。
2. **评审会手写派发文案**：手写必然夹带提交者的说法（「只是小改」「测试过了」），评审人会顺着叙事走，事后查不出哪些结论没有被独立验证。派发必须脚本生成。
3. **改一行也绕评审**：一旦开了「这么小的改动不用评」的口子，例外会膨胀到覆盖全部改动。纯文档是唯一例外，且要在 PR 正文声明。
4. **PR 走形式**：分支开了、PR 也开了，但门禁是在本地跑的、评审是提交者自己点的 APPROVE、合并前没有 rebase 到最新主干。这种 PR 只增加了仪式感，没有增加任何一个可审计的证据点——它和直推主干在生产事故面前是同一件事。

## 3. 一个可复制的评审样例

某次 PR 的评审结论原文（结构照抄，内容换成本仓库的）：

```
结论：APPROVE
复核动作：在本分支复跑 6 条门禁；通读 <文件> 的 diff；把上限从 1.000 改成 0.999 做变异实验
证据：<门禁原始输出 6 段>；变异后精确红 3 条，红的是 <用例名 1/2/3>，原文如下 …
```

关键在**变异实验**：不是「我读了一遍觉得对」，而是「我故意把它改坏，看门禁会不会红」。把上限改到刚好越界的值，红的条数必须可预期——对不上说明门禁有洞。这种做法成本很低（一次小改 + 一次回退），收益是把「看起来绿」变成「证明绿」。

## 4. 一个可复制的合并节奏

实录里十条线同时跑、合并只有一条队，结果是 15.1 分钟一张 PR 的中位间隔。这个数字反直觉的地方在于：**排队没有拖慢它**。原因是每条线在等合并的时候继续改下一条，而主干始终保持「门禁在最新基线上绿」这一条不变式。反过来，如果允许两条 PR 同时进主干，两条都要重跑，还要处理谁先谁后的冲突——时间花在返工上，比排队更贵。

## 5. 本仓库与实录的差异

- 实录用的是单一仓库的并行队列；本仓库是**技能仓库**，并行度本来就低，所以 `SKILL.md` §5 的分层规则在本仓库通常是「一轮只有一张单」——规则留着，不要因为平时用不上就删掉；
- 实录的门禁是它的构建与真机流程；本仓库的门禁是 `skill-authoring/scripts/check-skills.py` 与 publish-check；
- 实录的分支命名是 `type/378-slug`；本仓库沿用，但 `type` 取 `flow.md` 的「分层规则」一节列出的五种；
- 实录有维护者兜底；本仓库没有，所以 `SKILL.md` §11 的三层机制（平台保护 / 钩子 / 对账）不是可选项。
