# 标签台账与门禁守卫（ledger-and-gates）

> 状态不靠人记，靠标签表达；门禁清单只有一个事实源；合规不靠自觉，靠对账。本文件是 `SKILL.md` §4、§7、§11、§12 的执行面细则。

---

## 1. 标签就是任务队列

| 标签 | 含义 | 谁来动 | 离开条件 |
|---|---|---|---|
| `needs-repro` | 缺可粘贴的复现命令 | 发现者补齐 | 正文出现能跑通的复现命令 |
| `needs-fix` | 已确认，等代码线修 | 任一空闲会话 | 挂上 PR 编号 |
| `needs-review` | PR 已开，等新上下文评审 | 派发脚本 / 主控 | 出现三段齐全的结论 |
| `needs-merge` | 已 APPROVE，排进合并队 | 主控 | PR 合并完成 |
| `needs-live-verify` | 已合并，等真机回签 | 发现者或新会话 | 回签记录贴出且结论通过 |
| `blocked` | 被另一张单卡住 | 任意 | 依赖单关闭后摘掉 |

规则：

- **谁空闲谁捡**：空闲会话按标签顺序（`needs-fix` → `needs-review` → `needs-merge` → `needs-live-verify`）自取，不需要开会同步；
- **数字就是待办清单**：每次报告只报各标签的计数，不报状态描述；
- **一张单同时最多两个标签**，超出的标签表示这张单没拆干净；
- **标签不表达进度百分比**——进度体现在「有没有 PR、门禁绿不绿、有没有回签」；
- **`needs-merge` 是队列而不是进度条**：挂上它意味着「所有前置已完成，只等基线」，主控按存活时间最长优先合。

## 2. 门禁清单的唯一事实源

门禁命令写在仓库 `scripts/gates.json`（或等价的机器可读清单），**每个 PR 都读它**，文档里只写「门禁见清单」，不复制命令。

```json
{
  "baseline": "origin/main",
  "gates": [
    { "name": "lint", "cmd": "<lint 命令>", "required": true },
    { "name": "typecheck", "cmd": "<类型检查命令>", "required": true },
    { "name": "test", "cmd": "<测试命令>", "required": true },
    { "name": "build", "cmd": "<构建命令>", "required": true }
  ],
  "pr": {
    "protect": ["main", "master", "slim"],
    "merge": "squash",
    "reviewers": "new-context"
  }
}
```

`baseline` 与 `pr` 两段是把「合并前必须跑在最新主干上」「主干不许直推」「一张 PR 一个提交」写成机器可读的事实，脚本可以读它来决定怎么跑、怎么拦、怎么合。

纪律：

1. **改清单 = 改规矩**：放宽或删掉一条门禁，必须单独开一张单并走评审（`SKILL.md` §14 第 4 条）；
2. **文档不复制命令**：清单与文档不一致时以清单为准，并立刻修文档；
3. **PR 正文贴的是清单的输出**，不是每张 PR 自己发明的命令；
4. **清单里不写环境变量与凭据**——命令自取环境，清单只写命令本身。

## 3. 派发脚本的形态

用纯标准库脚本生成评审派发文案。要求：

- 输入只有 PR 编号（与可选的仓库标识）；
- 输出只含：PR 编号、分支名、改动文件清单、门禁命令清单、结论三段模板；
- **默认不给 PR 正文**，也不给 issue 正文；
- 输出可被直接粘贴进新会话作为任务说明；
- 脚本失败时报错退出，不输出半截文案。

脚本落在仓库 `scripts/`，形态要求见 `skill-authoring` 的 D7（Python 3 纯标准库单文件、kebab-case 命名）；`SKILL.md` 只写用途，不写命令行。

## 4. 拦推脚本与对账

`SKILL.md` §11 的三层机制里，第二层是钩子，第三层是对账：

- **钩子**：`scripts/deny-main-push.sh` 入库，安装到 `.git/hooks/pre-push`；形态与安装命令见 `pr-contract.md` 的「本地钩子」一节。
- **对账**：每轮收口跑一次，检查主干第一父链上有没有不带单号的提交；命令见 `pr-contract.md` 的「对账」一节。输出非空即一次违规，按那里的处置顺序收拾。

钩子挡手滑，平台保护挡习惯，对账挡「事后编故事」。三层都缺着的时候，别声称这套流程是「强制」的。

## 5. 每轮收口的四个数字

| 数字 | 从哪读 | 阈值（超出就停一轮） |
|---|---|---|
| 存活 PR 数 | 开着的 PR 列表 | 上限由项目自定；实测基线 10，超出说明合并在堵 |
| 合并间隔中位数 | 合并时间戳两两之差 | 基线 15.1 分钟；持续翻倍说明门禁在主干上反复红 |
| 单小时合并峰值 | 每小时合并数 | 基线 9 次；断崖式下跌说明评审队列积压 |
| 直推 / 孤儿提交数 | 对账命令输出行数 | **必须为 0**；非 0 是事故，当轮就要回溯并补机制 |

前三个数字异常时的处置顺序：先看 `needs-review` 积压 → 再看门禁红率 → 最后才考虑放宽并发上限。放宽并发永远不是第一个选项。第四个数字没有「容忍范围」，它是流程是否成立的判据本身。
