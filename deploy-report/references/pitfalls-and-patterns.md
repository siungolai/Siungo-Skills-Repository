# 部署坑与模式库（实战沉淀，脱敏）

> 本文件沉淀自多次真实服务器部署（含静态站与 Go/systemd 后端服务，公网可查事实保留，凭据全部剔除）。条数持续扩充，不写死。示例以泛化形式给出；标注"实例"的为真实项目结构（已脱敏）。

## 一、原子替换与"正在使用的文件"

1. **运行中二进制不能 cp 覆盖**：对正在运行的服务文件执行 `cp` 覆盖会报 `Text file busy` 或产生非原子替换。
   - 正确模式：**先传 /tmp → sha256 核对 → `mv` 现役为备份名 → `mv` 新文件到现役路径**（mv 同文件系统内是原子操作）。
   - 错误示范：`cp new-server /var/www/app/upload-server`（实例踩过：Text file busy）。
2. **传输先落临时路径，绝不直接覆盖现役**：SFTP/SCP 直接写目标文件不是原子的；一律先传 `/tmp/<app>-<ts>` 或目标目录旁的 staging 名，校验后再替换。
3. **校验和**：本地 `sha256sum` 产物并记录；上传后在服务器侧 `sha256sum` 比对一致才替换。

## 二、备份与保留

1. **先备份后动刀，备份失败即停**：任何替换/迁移前，现役文件必须先有备份，备份动作失败则终止部署。
2. 命名带时间戳且含描述：`<app>-<描述>-<yyyyMMdd-HHmmss>`（如 `upload-server-prewebp-20260901-103000`）。
3. 备份集中存放：服务器固定备份目录（如 `/root/<app>-deploy-bak/`），与部署目录分离。
4. **保留 N 份（默认 3）**：部署成功后清理最旧备份（`ls -1t | tail -n +N` 删除超出的最旧项），保留最近 3 份作为回滚窗口。
5. **时间戳传参陷阱**：命名里内联 `$(date +%Y%m%d)` 时，若命令经外层 shell（PowerShell 等）传参，`$()` 可能被外层解析成空/错误值（实例踩过）。做法：先在外层预生成时间戳变量，再拼入命令字符串。
6. 数据目录/数据库单独备份：活动文件只做副本（`cp`/`tar`），绝不原地覆盖或移动。

## 三、构建：本地还是服务器？

1. **判定**：纯静态资源（前端 dist/）→ 本地构建上传；需要平台相关的二进制（CGO、动态链接 glibc、平台特定依赖）→ **服务器构建**（本机 Windows 构建物不能直接用于 Linux 服务器）。
2. 服务器构建模式：源码打包上传 → 服务器安装目录构建 → 校验产物 → 原子替换。服务器需要工具链：确认时注意 **`which` 无结果 ≠ 未安装**——工具可能已装但 PATH 未包含（实例：服务器已有 Go 1.23 于 /usr/local/go，PATH 未含导致误判"未安装"）。
3. 服务器构建 CGO 程序需编译器与依赖（实例：gcc 14 + CGO_ENABLED=1 + `-ldflags="-s -w"`，产物为动态链接 ELF）。
4. 构建产物瘦身与一致性：`-ldflags` 去符号；构建前记录依赖版本（go.mod / package-lock）避免"本地能跑线上不能"。

## 四、服务与权限

1. **进程在 ≠ 正常**：重启后必须核验——`systemctl is-active`、监听端口、**启动后日志无新增错误**（`journalctl -u <svc> -n <行数> --since "<时间>"`），实例教训：只看进程存活漏掉了配置错误。
2. **systemd 强隔离（ProtectSystem=strict 等）**：服务只能写 ReadWritePaths 声明内的路径；部署文件若在只读区，属主与路径须与 unit 声明一致，否则启动即失败。
3. 属主一致性：上传/替换后检查属主（如 www-data），`mv` 会保留原属主时注意新文件属主是否匹配（必要时 `chown`）。
4. 静态站更新：tar 上传 → 解压到目标 → `nginx -t` 通过后 `nginx -s reload`；不要 kill nginx。

## 五、验证通道与假象

1. **本机工具通道限制**：本机 curl 对 HTTPS 可能受本地环境限制（如沙箱 schannel 失败）→ 用替代通道验证线上：Node https 脚本 / 浏览器 / 服务器本机 curl（实例：本机 curl HTTPS 全失败，线上验证改 Node https）。
2. **nginx try_files 假象**：路由前缀不对时，nginx 会对请求返回 404/405 而不是到达后端（实例：DELETE 请求漏掉 /api 前缀 → nginx 对 DELETE 直接 405，请求根本没到后端）。验证清单里的路径必须对照**真实路由前缀**写。
3. **异步任务 ≠ 提交即完成**：批量重建/迁移类任务，请求返回 2xx 只代表"已受理"；必须轮询到任务完成态（实例：重建 69/69 成功耗时约 59s，期间 2xx 无意义）。
4. 强缓存影响验证：产物带强缓存头时，浏览器/中间层可能命中旧版——验证关键产物变化时绕过缓存（加 query、禁缓存头）或直接验服务器响应。
5. 上传类冒烟会写生产数据：用例完成后必须清理测试数据（实例：测试照片删除走真实 DELETE 路由；清理动作要可核对）。

## 六、失败处理

1. 失败后先判断是"部署坏了"还是"验证方法误报"（缓存、前缀、通道），再决定回滚与否——**决定权在用户**，绝不自动回滚。
2. 单次重试需说明理由；连续失败不无界重试（网络故障等外部原因先报告）。
3. 回滚 = 恢复最近备份（`mv` 备份回现役名）→ 重启/重载 → T1 基础验收；回滚后保留现场证据（日志摘录）供排查。

## 七、测试与清洁

1. 部署前的本地测试要真实可复现：Go 测试需 GOCACHE/GOMODCACHE 指工作区并设 GOPROXY；npm 需缓存指向工作区（写用户目录被拒是常见沙箱现象）。
2. 前端构建产物验证：构建后用本地 preview + 代理核对 /api 与静态资源路径，再上服务器（比上线后才发现 404 成本低得多）。
3. 服务器不留临时文件：/tmp 与部署目录的临时包、测试数据在完成后清理，清理动作写入完成报告。

## 八、文档与基线

1. 无 git 项目用"里程碑节点 + 部署备份"代替版本记录：每次上线更新档案 `last_deploy` 字段或私有部署记录文档（什么时间、部署了什么、备份在哪、回滚过没有）。
2. 交接文档与部署档案分离：可公开的架构/流程进项目文档；含连接信息的进 gitignore 档案。
