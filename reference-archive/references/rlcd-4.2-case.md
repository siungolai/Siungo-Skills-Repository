# 实例：ESP32-S3-RLCD-4.2 归档（rlcd-4.2-case）

> 一个完整的真实案例，用来演示 §3～§5 各步骤在实操中长什么样。
> 归档产物本身不在本技能里（体积与版权原因），这里只保留**方法层面的证据与教训**。

---

## 1. 场景

- 目标：把某厂商的 4.2" 电子墨/反射式显示板开发板的**全部官方参考资料**离线化，为「后面要用新固件」做准备。
- 官方资料分布在四处：文档站（8 个页面）、GitHub 仓库（2667 个文件、282 MB）、GitHub Releases（2 个 release、25 个资产）、PDF 原理图与数据手册。
- 归档规模：11 个 Markdown + 49 张图片 + 35 个下载文件 + 2667 个源码文件 = 2762 个文件 / 338 MB。

## 2. 归档结构落地形态

```
.doc/ESP32-S3-RLCD/
├── README.md            索引（按用途导航 + 关键事实 + 自检表）
├── 01..09-*.md          官方原文存档（8 份）
├── 02/10-*.md           整理汇总（速查表 / 固件与烧录）
├── assets/              49 张（站点 webp + 本地化 png）
├── downloads/           原理图 + 数据手册 + 结构文件 + firmware/ + xiaozhi-board/
└── reference-source/    上游仓库 HEAD 全量快照
```

编号从 01 起连续；`02` 留给后来新增的「硬件速查表」——中途插入时把后续编号整体前移过一轮。

## 3. 四路交叉验证的实际结果

该板的总线与关键引脚最终由四路**逐项一致**确认：

| 路径 | 载体 | 形态 |
|---|---|---|
| ① 官方接口表 | 文档站接口介绍图 + 仓库 `docs/` | 位图，需定位网格线后逐格读 |
| ② 上游 BSP 源码 | `main/user_config.h`、`components/port_bsp/*.cpp`、`board_cfg.txt` | 文本，可 grep |
| ③ 上游第三方框架配置 | 仓库 `examples/esphome/*.yaml` | 文本，引脚写成配置项 |
| ④ 外部项目板级配置 | 某开源语音助手项目的 `config.h` / `config.json` | 文本，独立实现 |

**四路对齐的典型结论**（示例）：I2C SDA/SCL、I2S 五线、LCD 六线、SD 三线、功放使能、电平——逐项一致，无一例外。

**第 ③ 路的价值被低估**：ESPHome YAML 把每个引脚写成一行配置，是四路里**最容易机器比对**的一份。找第三方框架时先找它。

**第 ④ 路的价值在"独立"**：前 3 路都出自上游团队，可能一起错。第 4 路是别人照着官方文档写的，会漏抄、会按自己板子改——这正是它能暴露矛盾的原因。取它时注意上游路径会随版本变（旧版 `main/boards/...`，新版 `main/main/boards/...`），按目录名硬拼 URL 会 404。

## 4. 踩到的五个坑（都是实测出来的）

### 坑 1：接口表里的器件可能根本没焊

官方接口表有一整列给某 6 轴 IMU 预留，表里把 ESP32 的 I2C 引脚同时画在该列与扩展排针列。看起来装了 IMU。

**核对**：在原理图网表里检索型号串与常见别名（`QMI` / `8658` / `IMU` / `Accel` / `Gyro`）→ 全部零命中。

**结论**：**板上没有这颗器件**，那一列只是复用标注。官方接口表描述的是**信号分配**，不是**物料清单**。

### 坑 2：位图表格的表头会错位

表头错位后整张表语义全变，但**每一格看起来都「读得出值」**——最难发现的错误类型。

**对策**：读值之前先单独验表头：第一列是不是 GPIO 编号列、表头文字落在哪一列的 x 区间。定位网格线后按坐标归列，不要按肉眼顺序。

### 坑 3：PDF 文本层的引脚编号会错位

原理图 PDF 的文本层按绘制顺序而非电气连接顺序输出。抽出的网表里，连接器 FPC 的符号引脚号与网名的对应关系整体偏移了几位——看起来完全合理，但和原理图上印刷的脚号对不上。同一份网表里还出现「某个网挂着上百个引脚」的噪声（文本顺序问题，不是真实连接）。

**处置**：一旦发现编号错位，**该连接器的具体脚序不作为事实发布**，只发布「信号集合 + 连接器型号」，并明确提示接插件前对照原理图复核。

> 这条纪律的价值是实测出来的：FPC 脚序错一次，接插件就可能烧板子。**宁可少发布一条，也不要一条看着精确却错的脚序。**

### 坑 4：上游把目录整体改名，代码一个字节没动

官方仓库把一个 255 文件的目录整体改名，其中 253 个文件 sha1 完全一致，只有两个 README 变了。

**如果不逐文件 sha1 对账**，这看起来像一次大改，人会顺手把技术结论也一起改掉——而实际上技术内容根本没变。

**对策**：对账脚本必须输出「上游有本地无 / 本地有上游无 / 两边都有但 sha1 不同 / sha1 相同」四类，而不是一个总数。总数区分不了「改了一行注释」和「换了整个驱动」。

### 坑 5：官方文档自身的缺漏

- 某页末尾写「请参考详细教程：\*\*\*\*。」——原页面即如此，链接是空的；
- 某处提到有编译好的固件，但官方页没给二进制地址；
- 板上有丝印标注清楚的 8 位拨码开关，官方文档与上游代码里都**没有对应实现**。

**处置**：前三类按「原页面即如此」保留并注明；最后这类**不写进事实表**，只进不确定项，写明「官方无对应实现」。

## 5. 增量对账实例

对账对象：上游仓库 HEAD vs 本地归档快照。产出三张表后，流程是：

1. 先看「上游有本地无」——本次新增 258 个文件，其中一个 251 文件的目录是**新增的出厂固件工程**；
2. 再看「本地有上游无」——本次删除 1603 个文件，其中 1348 个是旧版第三方 AI 固件的源码副本；
3. 用 sha1 把删除集与新增集做同名同哈希配对 → 255 个文件路径一一对应、逐文件 sha1 完全一致，**判定为目录改名搬家，代码未变**；
4. 只有两个 README 真的变了 → 文档里只更新提到路径的部分，技术结论一条不动。

## 6. 不确定项清单的形态

最终归档里有两处显式的「不要当作事实使用」：

| 项 | 冲突在哪两方 | 判定需要什么条件 |
|---|---|---|
| 触摸 FPC 的具体脚序 | 原理图 PDF 文本层编号错位 vs 符号印刷脚号 | 对照原理图 PDF 原图人工逐脚复核（实物接插件前必须做） |
| 某 6 轴 IMU 是否存在 | 官方接口表有该列 vs 原理图无此器件 | 实物确认板上是否焊有该器件 |
| 屏幕分辨率写法不一 | 官方 `user_config.h` 写 300×400 竖屏 vs 官方 `main.cpp` 与全部例程用 400×300 横屏 | 无需判定——两个都记并注明差异，不替官方选一个 |
