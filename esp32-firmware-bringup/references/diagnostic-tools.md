# 诊断工具台（diagnostic-tools）

> `SKILL.md` §5 的完整版：七个诊断工具的用途与共性约定、错误码判读表、从机离线保护原理，以及「先物理层后固件」这条阶梯的每一步怎么落地。删掉本文件，主流程仍可执行，但会失去工具清单与判据细节。

---

## 一、诊断阶梯（顺序即纪律）

**通断确认之前，地址扫描与日志全是无效劳动。**

| 层 | 判什么 | 用什么 | 通过标准 |
|---|---|---|---|
| 1. 电源真值 | 供电真的到了器件吗 | 万用表量 VCC/GND | 电压符合，不是「灯亮」 |
| 2. 通断 | 信号真的接到了器件吗 | 万用表通断 | 排针对应针导通，无虚接 |
| 3. 总线静态电平 | 上拉在线吗 | `bus-probe` / `link-probe` | `pullup=HIGH` |
| 4. 地址扫描 | 器件在这个地址吗 | `i2c-scan` | 期望地址有应答 |
| 5. 错误码判读 | 卡在哪一层 | `endTransmission()` 返回值 | 见下表 |
| 6. 固件 | 前面都过了才看 | 串口日志 + 逻辑 | — |

**典型反例（真实教训）**：1602 背包模块「背光亮 + 两线 HIGH + 全段无应答」，当时收敛到「模块硬件故障」。反证是把背包整块拔下来，**背光仍亮、两线仍 HIGH**——背光由背包上 PCF8574 的 P7 驱动，器件真拔掉不可能还亮。真相是排针没插到底或 16 针并口虚接，电流从未经过 PCF8574。

**「背光亮 = 供电到位」不成立**；上拉读到 HIGH 也不能证明 SDA/SCL 真接到了背包。所以阶梯第 1、2 层排在仪器判读之前。

## 二、错误码判读表

`Wire.endTransmission()` 返回值直接决定下一步查哪里：

| 码 | 含义 | 动作 |
|---|---|---|
| 0 | 成功 | — |
| 1 | 数据过长 | 查代码 |
| **2** | **该地址无应答**（器件不在这个地址） | 查器件供电、焊接、地址跳线 |
| 3 | 数据无应答 | 查从机状态与总线 |
| 4 | 其它 | 查总线状态 |
| **5** | **总线超时**（事务根本没法完成） | **停止查地址，直接查物理层** |

**判错码 = 白干**。全段都是 5 时翻地址表，是最常见的时间浪费。

反过来说：`i2c-scan` **零应答且零 `[ERR]` 行**，说明总线电气与主控收发都正常——此时不要再查主控侧，直接查器件供电与焊接。

## 三、七个诊断工具

每个自带 `platformio.ini` 可独立烧录。**共性参数**：`PIN_I2C_SCL=4`、`PIN_I2C_SDA=5`（`dht-probe` 除外）、`SERIAL_BAUD=115200`、`Wire.setTimeOut(50)`。`i2c-scan` 扫描速率用 **100kHz** 而非 400kHz（扫描阶段优先容错）；`bus-probe` / `link-probe` 每 3000ms 复测一次。

| 工具 | 位置 | 判什么 |
|---|---|---|
| `i2c-scan` | `uptime-oled/tools/i2c-scan`、`lcd1602-uptime/tools/i2c-scan` | 扫 0x08–0x77 逐地址应答 |
| `bus-probe` | `uptime-oled/tools/bus-probe`、`dht11-oled/tools/bus-probe` | SCL/SDA 静态电平（`pullup` vs `float`） |
| `link-probe` | `lcd1602-uptime/tools/link-probe` | 1602 总线上拉判读 |
| `power-probe` | `lcd1602-uptime/tools/power-probe` | 供电链路检查 |
| `dht-probe` | `dht11-oled/tools/dht-probe` | DHT11 数据线上拉判读 |

**`tools/` 放独立小工程，不放 `src/`**——同一个 `src/` 里两个 `setup()`/`loop()` 会直接链接失败。

## 四、从机离线保护

`flush()` 发 8 页 × 2 次 I2C 事务。从机不在线时每页 `endTransmission()` 阻塞到 50ms 超时，一轮刷新 ≈ 800ms，足以把 1 秒节拍带偏。50ms 的来源就是 `Wire.setTimeOut(50)`：8 页 × 2 次事务 × 50ms。

**解法**：探测失败后刷新函数直接返回，不发任何事务。实测屏缺席仍 45 tick / 45 秒 = 1.0000 tick 每秒，无漂移——计时精度与屏幕在线状态完全解耦。

## 五、日志判读约定

- **ASCII 不用中文**：UTF-8 到部分串口工具变乱码，而故障信息恰是唯一线索；
- **无效读数写 `--` 不写 0**：0°C 是合法读数，写 0 就跟没读到混在一起；
- **刷新计数 `#N` 是现场证据**：数字在跑说明刷新周期真在跑。LCD 掉电后画面会保留，静止的字不能证明刷新在跑；
- **定长覆盖**：每行补空格到满列，防上一帧残影；
- **两类串口行分开**：节拍行（每次刷新）与采样行（每次采样，固定字段 CSV）不混，`grep -c 'ok=1'` 直接统计成功率；
- **数据年龄角标**：0s 起每秒 +1，上限 99s——读数有多旧一眼可见；
- **降级显示**：湿度失效时大号位降级显示温度，两个都没有显示 `--`。

## 六、本机沙箱边界

- `workspace-write` 下 `~/.platformio/platforms.lock` 写入被拒，编译需 `danger-full-access`；
- `pio device monitor` 不能在管道/重定向下用，读日志用 Python + pyserial 直读串口；
- PowerShell 管道按 GBK 解码外部输出，UTF-8 中文显示乱码（仅显示问题，不影响写入）。
