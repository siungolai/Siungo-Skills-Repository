# 隐私拦截按「托管与可见性」双条件分级

`commit-report` v1.4.x 对隐私与凭据只有一档处置：命中即拦，与提交推到哪台服务器无关。v2.0.0 引入一条前置判定（`SKILL.md` §1.6，细则见 `references/host-visibility.md`），把落地目标分成公共托管与私人托管两类，并在「私人托管 ＋ 私有仓库」这一种组合下把隐私类命中降为提示。凭据类不参与降级——任何托管下都硬阻断。

支持这条分级的论据有三：其一，隐私值的暴露面确实取决于谁能读到目标仓库，自建服务器上的私有仓库没有第三方平台、CI 与镜像挂在数据链上；其二，凭据的被害人数不随仓库可见性变化（协作者、备份、将来转公开都会经手它），且泄露后唯一有效的止损手段是轮换，与托管位置无关，所以两类必须分开；其三，把两者合并在同一档，会逼用户在一台只有他自己能访问的服务器前也做一次无意义的逐条确认，久而久之整套闸门会被当成噪声。

被否决的替代方案有两个。一是**只看仓库可见性**（private 就放宽）：private 只是一个开关，转公开既不必经过用户同意，也不必经过这次审阅，它是状态不是边界。二是**对公共托管上的 private 仓库也放宽**：收益太小而代价是整条数据链——用户 GitHub 上的仓库目前全部是公开的，这条分支一次都不会触发；反之一旦触发，代价是一次不可逆的暴露。判定失败一律 fail-closed 按公开处理，解除路径写成一句话（在仓库里声明一次，或回复里明说这是自己的服务器），避免闸门卡死后没有出口。
