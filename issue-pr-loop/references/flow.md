# 流程细则（flow）

> 本文件是 `SKILL.md` 各章的展开：判据之外的操作细节、模板、落点。`SKILL.md` 写「做什么、什么时候算过」，这里写「具体怎么写、放在哪、反例长什么样」。

---

## 1. 五步主流程的形态

```
发现缺陷或需求
   ↓
issue：四要素            ← 一张单只装一件能独立验收的事
   ↓
plan 追评：方案 + 复现结果
   ↓
worktree：<type>/<单号>-<slug>
   ↓
PR：正文分段 + 门禁绿
   ↓
新上下文评审：结论 / 复核动作 / 证据
   ↓
合并（同一时刻只有一条队）
   ↓
改运行时行为？→ 是：挂 needs-live-verify，换人回签后才关单
              → 否（纯文档 / 纯重构）：Closes 直接关
```

五步里**没有一步需要维护者逐张点头**：评审交给新上下文，回签交给发现者或另一个新会话。这是并行能持续的前提；凡是需要人做闸门的环节，都会变成队列的瓶颈。

## 2. 开单（`SKILL.md` §2 展开）

### 2.1 四要素

| 要素 | 写法 | 反例 |
|---|---|---|
| 现象 | 谁、在什么操作下、看到什么 | 「UI 有点怪」 |
| 期望 | 应当看到什么，可核对 | 「修一下进度环」 |
| 复现命令 | 一行可复制粘贴、能独立跑 | 「我这边能复现」 |
| 影响面 | 哪些路径 / 平台 / 用户受影响 | 空缺 |

复现命令**先自己跑通一次**再贴进去。贴了没跑过的命令，等于把复现成本转给下一个会话，而下一个会话一定会打回 `needs-repro`。

### 2.2 拆分信号表

| 信号 | 处理 |
|---|---|
| 改了多个不相关文件 | 拆成多张单 |
| 验收要跑两轮真机 | 按轮次拆 |
| 一半能今天合，一半要等结论 | 拆开，别互相等 |
| 同一处缺陷的第二例 | 新开一张，互相引用 |
| 一张单需要两个不同技能域的人 | 拆成两张，用依赖边串起来 |

### 2.3 批量出单

开单慢，多半是**边想边写**。改成集中产出：一次审计、一轮真机、一次日志判读，先把清单列全，再统一成单。

1. 先写**母单**：范围、判据、子单清单；
2. 按分节拆**子单**，正文首行 `Refs #<母单号>`；
3. 统一打标签（见 `ledger-and-gates.md` §1）；
4. 一次性提交，统一回贴到母单评论里。

## 3. plan 追评（`SKILL.md` §3 展开）

plan 是 issue 里的一条评论，不是新文件。模板：

```markdown
## plan

**改哪里**：<文件清单，逐个一句话>
**为什么是这几个**：<根因判断 + 排除掉的其他可能>
**门禁**：<要跑的命令清单，与仓库门禁清单一致>
**回滚**：<怎么撤，撤完怎么验>
**验收人**：<谁在什么环境下复跑哪条命令>
```

plan 评论之后可以追加**复现结果**评论：贴原始输出，不贴结论。结论放评审里。

判据：新会话读完正文 + plan 就能开工，不必询问任何口头约定。

---

## 4. 派活与分层（`SKILL.md` §4 展开）

### 4.1 一轮盘点的三个问题

1. 本轮有哪些单子是「母单 + N 张子单」的同一轮产物？
2. 哪些子单改同一个文件，或互为前提？
3. 哪些单子没有依赖边、可以同层同时开？

### 4.2 分层规则

- **同文件永不同层**：改同一文件的两张单，无论看起来多独立，都排成上下层。
- **被依赖方先派**：B 依赖 A 的产出（接口、常量、schema），A 先合，B 再开。
- **整层同时派**：同层内全部同时开 worktree，不等谁先完成。
- **一目录一分支**：worktree 命名 `<type>/<单号>-<slug>`，type 取 `feat` / `fix` / `refactor` / `docs` / `test`。
- **自跑门禁**：每条线自己跑全套门禁，不交给主控会话跑（主控会被等待卡住）。

### 4.3 主控会话的边界

主控只做四件事：盘点依赖、派发、收结论、决定合并顺序。主控一旦动手改代码，就不再是并行队列的调度者，而是队列里的一个执行者——此时它必须把自己也当成一条线，遵守同文件不同层的规则。

## 5. PR 正文（`SKILL.md` §5 展开）

```markdown
## 问题
<对应 issue 的现象，一句话；`Refs #nnn` 或 `Closes #nnn`>

## 改动
<文件清单 + 每处一两句；与 plan 不一致的地方要明确写出并说明原因>

## 验证
<门禁原始输出，逐条贴；不要写「已通过」两个字>

## 回签
<改运行时行为时写：待 needs-live-verify，回签命令是 __；纯文档/重构时写：不涉及>
```

---

## 6. 评审派发（`SKILL.md` §6 展开）

### 6.1 派发物料的最小集

派发文案只给：**PR 编号、分支名、改动文件清单、门禁命令清单**。**不给 PR 正文**——评审人自己去读。给正文等于给了提交者的叙事，评审会不自觉地顺着叙事走。

派发文案由脚本生成，脚本落在仓库 `scripts/`（形态要求见 `ledger-and-gates.md` §3）。手写派发是流程腐化的第一步。

### 6.2 结论三段

| 段 | 判据 | 反例 |
|---|---|---|
| 结论 | 只能是 `APPROVE` 或 `CHANGES-REQUESTED` | 「看起来没问题」 |
| 复核动作 | 亲自跑了什么、读了哪些文件，逐条列出 | 「已 review」 |
| 证据 | 门禁原始输出 / 文件行号 / 反例复现 | 「测试过了」 |

**证据必须包含评审人自己跑出来的东西**。真实例子里，评审会话自己复跑了 6 条门禁，还做了一次变异实验——把上限改成 0.999，精确红 3 条，贴出原文，才给 APPROVE。这样的结论提交者可以直接合并，不必二次询问。

### 6.3 评审权外包的意义

评审权外包不只是省人工，它是**并行能持续的关键一环**：主控不等评审结果，评审在另一条线上进行，结论回来再决定合并顺序。

## 7. 串行合并（`SKILL.md` §7 展开）

- 同一时刻最多一条 PR 进主干；
- 合并前必须把门禁跑在**最新主干**上（rebase 或 merge base 再跑），贴原始输出；
- 合并后主干门禁再跑一遍，红了下一条线全部暂停；
- 一次合并只合一张，不合多张；
- 合并顺序按「被依赖方 → 依赖方」与「存活时间最长优先」两条排序。

原因一句话：门禁要跑在最新主干上，两条 PR 同时进主干，谁先谁后都得重跑。排队合并反而更快。

---

## 8. 回签与关单（`SKILL.md` §8 展开）

| 改动类型 | 关单写法 | 回签 |
|---|---|---|
| 纯文档 / 纯重构 | `Closes #nnn` | 不需要 |
| 改运行时行为（含配置、迁移、对外输出） | `Refs #nnn` + 合后挂 `needs-live-verify` | 必须换人真机回签 |

回签记录模板：

```markdown
回签：<人/会话标识>  环境：<机器 / 版本 / 数据>
复跑命令：<复制粘贴即用>
原始输出：<贴原文>
结论：通过 / 不通过（不通过则重开单并挂 needs-fix）
```

## 9. 记忆外置（`SKILL.md` §9 展开）

### 9.1 文件落点

| 文件 | 职责 | 建议落点 |
|---|---|---|
| 总纲 | 硬约束 + 五步流程总览 + 指向下面三份 | 仓库根 `AGENTS.md` 或 `CONTRIBUTING.md` |
| issue 指南 | 四要素、拆分信号、`needs-repro`、回签模板 | 文档目录 `ISSUE_GUIDE.md` |
| PR 指南 | 正文分段、合并条件、基线与门禁 | 文档目录 `PR_GUIDE.md` |
| 评审派发契约 | 派发物料、结论三段、独立性与回退 | 文档目录 `REVIEW_DISPATCH.md` |
| 门禁清单 | 门禁命令的唯一事实源（每个 PR 都读） | `scripts/gates.json`（脚本消费，不进文档树） |

文档目录名跟随仓库既有习惯（`doc/` 或 `docs/`），**换仓库只换目录**，四份文件本身同名。

### 9.2 接手六步

1. 读总纲，只看红线和五步；
2. 找一张已关闭的 issue，看四要素；
3. 在它下面找 plan 评论，看方案怎么定；
4. 打开对应 PR，看评审结论长什么样；
5. 自己开一张单，只写现象和复现命令；
6. 用派发脚本派一轮评审。

第 6 步走通，新会话即进入并行队列。这套流程**不要求接手者记住任何历史**，只要求把该写的写进单子里。
