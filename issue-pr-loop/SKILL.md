# issue-pr-loop：一单一活，并行改，串行合

> ⚠️ **触发加载检查**：收到任何「把这几件事拆成 issue / 开单派活 / 并行开发 / 建一套 PR 与评审规矩 / 谁来做回签」类意图时，**先确认本技能已加载**——若本技能不在当前会话的可用技能列表里（技能快照可能早于本技能安装或更新），先用当前环境的技能加载机制加载它，然后按其流程执行。切忌在未加载技能的情况下直接开单、改主干或合并 PR。

定位：本技能管**流程与队列**——单子怎么切、活怎么分层派、评审交给谁、合并怎么排队、状态怎么用标签表达。它不教怎么写技能（`skill-authoring`）、不教怎么改领域模型（上游技能 `domain-modeling`）、也不替用户做技术决策（那是 `grilling`）。核心机制是一条硬律：**并行只靠三件事——单子能独立、依赖先摸清、合并只排队**。流程细节见 [`references/flow.md`](references/flow.md)，台账与守卫细则见 [`references/ledger-and-gates.md`](references/ledger-and-gates.md)，实测基线与反例见 [`references/case-book.md`](references/case-book.md)，版本历史见 [`references/version.md`](references/version.md)。

**来源**：本流程提炼自一份公开的并行协作实录（wiredraw 5 天 502 次提交）——数字与形态见 `references/case-book.md`，本仓库没有照搬它的仓库名与分支名。

## 1. 何时使用

| 情形 | 动作 |
|---|---|
| 「这几件事开成 issue」「一轮审计 / 一轮真机出了 20 个问题」 | 走 §2 开单，一次集中产出 |
| 「先把方案定下来」「plan 写哪儿」 | 走 §3 追评 plan |
| 「几个会话一起改」「并行开跑」 | 走 §4 摸依赖分层派 |
| 「开 PR / 评审走了没有 / 谁来评」 | 走 §5 PR 与 §6 新上下文评审 |
| 「能合了吗」「几条 PR 一起进主干」 | 走 §7 串行合并 |
| 「合并后要回签吗」「这张单能关吗」 | 走 §8 回签与关单 |
| 「换个会话接手」「让新人/新 agent 上手」 | 走 §9 四文件接手 |
| 「改代码 / 写设计文档 / 提交推送本身」 | 不属于本技能；分别交给实现会话、`design-doc-review`、`commit-report` |

## 2. 开单：粒度决定并行度

一条 issue 只装**一件能独立验收的事**。判据三条同时成立才算合格：**能单独跑门禁**、**能单独合并**、**能单独回滚**。任何一条不成立就继续拆（`references/flow.md` 的「拆分信号表」一节）。

- 母单先定范围，子单在正文首行带父单号；
- 正文四要素：**现象 / 期望 / 复现命令 / 影响面**。复现命令先自己复制粘贴跑通，再补证据；
- 批量出单：一次审计或一轮真机集中产出一批，不要边想边写；
- 同一处缺陷的第二例新开一张、互相引用，不要塞进原单；
- 缺可粘贴复现命令的单立刻打 `needs-repro`。

**判据**：每张单都能被另一个会话在不读对话历史的情况下验收。

## 3. plan 追评：方案与复现结果写回单子

方案在 issue 里以 **plan 评论**定形，不在聊天里定形。plan 至少回答：改哪些文件、为什么改这几个、门禁怎么跑、失败时怎么回滚、验收由谁做。plan 与 issue 正文冲突时改的是 plan，不悄悄改正文。

**判据**：新会话读完 issue 正文 + plan 评论即可开工，不必回看对话。

## 4. 派活：先摸依赖，再分层

主控会话**不写代码**，只管顺序。每轮开跑前先盘点一次：本轮涉及的单子有没有改同一个文件的、有没有互为前提的。

- 改同一个文件的两张单**永不同层**——这条比依赖图更省事也更准；
- 有依赖边先派被依赖方，再派依赖方；无依赖边的整层同时派发；
- 每个执行线一个 **worktree**（一目录一分支，命名 `<type>/<单号>-<slug>`），坏了删掉重来；
- 执行线各自跑门禁、各自出 PR，互不等待。

**判据**：派发表上没有任何两条同层并行线触碰同一文件。

## 5. PR：正文分段，门禁先行

PR 正文固定分段：**问题 / 改动 / 验证**（门禁原始输出）/ **回签说明**。缺哪一段就不进评审队列。门禁清单的唯一事实源是本仓库的守卫脚本，不是文档（见 `references/ledger-and-gates.md` §2）。

**判据**：本分支上全部门禁绿，且正文三段齐全。

## 6. 评审：外包给新上下文

派评测人一律**新上下文**，且执行线与评审人**不得是同一个会话**。派发文案由脚本生成，不手写——手写必然夹带提交者的说法，事后无法核查。评审结论必须三段齐全，缺一段视为未评审：

```
结论：APPROVE / CHANGES-REQUESTED
复核动作：<亲自跑了什么、读了哪些文件>
证据：<门禁原始输出 / 文件行号 / 反例复现>
```

**判据**：结论行可被机器 grep；证据里至少有一样是评审人自己跑出来的，不是抄 PR 正文的。

## 7. 串行合并：改的时候十条线，合只有一条队

同一时刻最多一条 PR 进主干。门禁必须跑在**最新主干**上，两条 PR 先后进主干都得重跑——所以排队合并反而更快。

**判据**：合并前在最新主干上重跑门禁并贴出输出；合并后主干门禁仍绿。

## 8. 回签：行为类改动不许自签

`Closes` 只给**纯文档与纯重构**。凡改动运行时行为（含配置、数据迁移、对外输出），一律 `Refs`，合并后挂 `needs-live-verify`，由**发现者或另一个新会话**在真机上复跑复现命令回签，回签通过后才关单。**修复者不能给自己回签。**

**判据**：每张行为类单的关闭理由里有一条真机回签记录，执行者 ≠ 修复者。

## 9. 记忆外置：接手只要四个文件

流程状态全部落在仓库里，不落在会话记忆里。基线四个文档 + 一个门禁清单 + 一个派发脚本，各自职责与落点见 `references/flow.md` 的「记忆外置」一章。接手清单是固定六步（读总纲 → 读一张已关闭单 → 读它的 plan 评论 → 读对应 PR 的评审结论 → 自己开一张只有现象与复现的单 → 跑一次派发），第六步走通即进入并行队列。

**判据**：一个全新会话在零历史的前提下，能在 6 步内产出一张合格的单并派出一次评审。

## 10. 安全边界（硬性，任何路径下均适用）

1. **不替用户合并与推送**——合并、推送、关单属不可逆动作，须用户明确授权；授权一次只覆盖一轮。
2. **行为类不许 `Closes` 自关**——见 §8；自签等于取消真机验收。
3. **不改门禁清单去让红变绿**——放宽门禁必须单独开一张单并走评审。
4. **不绕过评审会合**——「改一行」也要新上下文结论；例外只有纯文档，且需在 PR 正文声明。
5. **同一文件不同层是违约**——发现已同层并行改同一文件，立刻停一条线、等前一条合完再继续。
6. **不把对话历史当交接材料**——没写进单子的决定等于没发生。
7. **派发文案不许手写**——手写会夹带提交者说法，评审结论失去独立性。

## 11. 完成后报告

一轮（开单 / 派活 / 评审 / 合并 / 回签）收口时一次性报告：

1. **本轮产出的单子**：新建 / 关闭 / 新挂标签各几张，编号范围；
2. **分层与派发**：本轮几层、哪些单同层、有无同文件冲突；
3. **PR 状态**：存活 PR 数、门禁状态、评审结论分布（APPROVE / CHANGES-REQUESTED / 未评）；
4. **合并记录**：合并了哪几张、合并前主干门禁输出；
5. **回签与遗留**：`needs-live-verify` 剩余清单及各自下一步；
6. **台账更新**：`README` / `CONTRIBUTING` 与门禁清单是否已同步（说明未同步的原因）。
