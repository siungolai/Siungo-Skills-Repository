# Web 设计文档审计模式

Web 开发项目（API 设计、数据模型、系统架构、PRD）设计文档审计模式。随更多 Web 项目审计逐步填充。

## 替换点提示

- **配置一致性**：把「配置键/值」换成你项目里的实际配置源（env / yaml / db / feature flag）。
- **API Schema 验证**：endpoint/handler 模式适用于任何 HTTP/gRPC/GraphQL 接口。
- **数据模型交叉引用**：表/模型定义适用于 SQL、ORM、schema registry 等任何数据层。
- **权限与访问**：权限档位适用于 RBAC/ABAC/租户隔离等任意权限模型。
- **性能约束**：N+1 / 分页 / 缓存 / 加载预算适用于任何后端服务。
- **错误处理 / 边界情况 / 迁移与兼容性**：跨项目通用，直接套用。

## 配置一致性

- 核验文档中引用的每个配置键在实际配置文件里存在
- 核验文档中的每个配置值与实际值一致
- 检查陈旧配置键（文档引用但配置已删）
- 检查缺失配置键（配置里有但文档未写）

## API Schema 验证

- 文档中的每个 endpoint 在代码里都有对应 handler
- 每个请求参数都在 handler 里做了校验
- 每个响应字段都与实际响应形态一致
- 版本化：检查是否有未文档化的破坏性变更

## 数据模型交叉引用

- 数据模型中的每个实体都有对应表/模型定义
- 数据模型中的每个字段都在某处被使用（无死字段）
- 每个外键都能解析到真实实体
- 枚举值在数据模型与代码之间一致

## 权限与访问

- 文档提到的每个权限在代码里都存在
- 每个权限检查都真的执行了（无信任客户端模式）
- 权限档位可达（不要要求任何用户角色都没有的权限）
- 角色流转有文档（用户如何获得/失去某角色）

## 性能约束

- 文档中的数据库查询要分析 N+1 模式
- 分页：每个列表 endpoint 都必须有分页
- 缓存：昂贵计算必须有缓存策略
- 加载时长：初始加载预算、懒加载阈值

## 错误处理

- 每个错误情况都要文档化（不只 happy path）
- 错误码在前端与后端之间一致
- 重试逻辑：哪些错误可重试，哪些不可
- 超时行为：客户端超时 vs 服务端超时 vs 外部服务超时

## 边界情况

- 空状态：列表为空、字段为 null 时怎么办
- 并发：两个请求竞争时怎么办
- 时区：跨时区的日期如何处理
- 字符编码：非 ASCII 字符、长字符串怎么办

## 迁移与兼容性

- Schema 迁移：每个变更都要有迁移路径
- 向后兼容：旧客户端必须仍能工作（或显式标记为破坏性变更）
- 数据回填：迁移时已有数据如何处理
- 回滚：迁移失败时如何撤销

## 常见陷阱

- 写「应该发生什么」而不是「实际发生什么」
- 假设前端校验足够（服务端也必须校验）
- 文档里硬编码本该由配置驱动的值
- 缺示例：每个 API endpoint 至少要有一个请求/响应示例
