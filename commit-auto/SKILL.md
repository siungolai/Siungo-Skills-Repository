# commit-auto：节奏驱动的自动提交

> ⚠️ **触发加载检查**：收到「自动提交 / 每完成一个功能就提交 / 不用每件事都问我」类意图，或处于已授权会话中某个功能刚闭合的时刻，**先确认本技能已加载**——若本技能不在当前会话可用技能列表（技能快照可能早于本技能安装/更新），先执行 `skills_list` 查证、再用 `skill_view(name='commit-auto')` 加载，然后按其流程执行。切忌在未加载技能的情况下自行提交。

定位：与 `commit-report`、`deploy-report` 构成三段分工——本技能管变更**以什么节奏进入仓库**（何时提交、如何切分），`commit-report` 管变更**能否**进入仓库（审阅门与执行），`deploy-report` 管变更**何时**进入线上。节奏这一层是本技能的全部新增内容；执行环节读盘复用 `commit-report`，风格匹配、两区审阅模板、推送降级通道与安全边界都只有它那一份事实源。术语见 `CONTEXT.md`，决策理由见 `docs/adr/`，版本历史见 [`references/version.md`](references/version.md)。

## 一、授权（总开关）

### 1.1 会话级授权

授权存在时，本技能按下面的节奏工作；授权不存在时，本技能不产生任何提交动作，把提交交回 `commit-report` 的逐次确认节奏——**不是不提交，而是回到「你开口我才提交」**。

- **算授权的表达**：含自动提交意图的明确指令——「这个会话你自动提交」「每做完一个功能就 commit，不用问我」「本会话的改动你直接提交」。判定沿用 `commit-report` 的「确认判定（操作性定义）」：纯模糊应答不算授权（单独一个「嗯」「可以」「继续」都不构成）。
- **会话边界**：一次连续会话（含 goal 自动续跑、含上下文压缩后）算同一会话；新开会话或上下文清空，授权随之失效。
- **覆盖范围**：commit，以及当前工作目录所在的那**一个**仓库。
- **撤回**：用户说「停止自动提交」「改回逐次确认」即刻失效。
- **跨仓库**：会话内发现第二个仓库有改动时，报告并问一句「另一个仓库 X 也有改动，是否一并纳入本次授权？」；得到确认后，那个仓库独立走一遍本流程。

### 1.2 措辞纪律

本技能**允许模型自动调用**（未设 `disable-model-invocation`），所以**加载 ≠ 已授权**：被加载只说明情境相关，授权必须由用户的话确认。

拿不准就按未授权处理，并问一句「要我从现在起自动提交吗？」。此前会话给过的授权，只在那次会话内有效。

### 1.3 仓库前置自检

1. 当前工作目录在 git 仓库内 → 采用该仓库；
2. 不在 git 仓库内 → 报告「当前目录不是 git 仓库」，结束；
3. detached HEAD → 报告并要求先切分支，结束；
4. 空仓库（无提交历史）→ 交给 `commit-report` §1.2 的首次提交处理。

### 1.4 状态快照

每次判定前先读三项：分支名与上游（`git rev-parse --abbrev-ref --symbolic-full-name @{u}`）、本地领先上游的未推送提交数（`git rev-list --count @{u}..HEAD`，无上游记 0）、工作区与暂存区变更（含未跟踪文件）。

领先提交只报告，不阻断——push 不在本技能范围内，领先与否不影响新提交的判定。

## 二、提交单元的判定

**没有信号就不提交；沉默是默认行为。**

### 2.1 功能完成信号（取第一个成立者）

1. **用户验收**——用户明确说这个功能好了、验收通过；
2. **测试与构建全绿**——该功能有对应测试（`go test`、`api-test.sh`、`smoke.sh`、`vitest` 等）且刚刚跑过、全绿；
3. **spec 条目交付完毕**——一个 ticket／spec 条目／阶段编号（`S5`、`V1.4 第 3 批`、`M2` 这类）完整落地；
4. **兜底**——一个自洽的改动已闭合，且下一步明显是另一个功能。

### 2.2 排除项

以下都不构成信号：agent 写文件的批次、一次工具调用完成、agent 自己的完成感、还没被看过的半成品。

### 2.3 多单元并存

工作区同时躺着多个未闭合单元时，只处理已经闭合的那一个，其余留在工作区并计入「未纳入清单」。

多个单元都已闭合时，逐个提交，一个单元一笔，顺序按依赖关系。拆分的边界由人的意图决定，agent 猜错会切出两笔都说不清的提交——拿不准就合并报告并询问。

### 2.4 无改动可提交

判定出的单元没有任何待提交改动时，报告「无事可提交」并结束。

## 三、范围切分

1. **显式路径清单**：以一个提交单元的文件清单为准，逐一列出路径。
   - **路径一律用 `-z` 读**：`git status --porcelain=v1 -z --untracked-files=all`。默认输出会把含中文或空格的路径加引号并转成八进制转义（`"docs/0001-\350\212\202....md"`），按行切分拿到的是**假路径**，后续检查会静默落空。
   - 在文件系统上核对时用不解释通配符的方式（PowerShell 用 `-LiteralPath`）。
   - **每条路径都必须真实命中**：任何一条落空即判定「扫描不完整」，中止并报告。静默跳过会让 §五 的红线扫描留下盲区。
2. **排除项**：按 `references/exclusions.md` 核对，命中的条目从提交范围剔除并计入报告。
3. **`.gitignore`**：发现垃圾反复出现时只报告；补规则是独立一笔 `chore: .gitignore …` 提交单元，与功能提交分开——它可以在下一个提交单元闭合时一并提出，但不并入那笔功能提交的 diff。
4. **未纳入清单**：列出未闭合单元、被排除的垃圾、被红线拦下的条目。

## 四、提交（读盘复用审阅门）

这里**读盘复用** `commit-report` 的流程，而不是「调用」它——它自带的流程要求逐笔等待用户确认，直接调用会把等待带进自动节奏；读盘复用只借用它的分析与文案规则，确认由会话级授权覆盖（ADR-0002）：

1. 读 `commit-report/SKILL.md`：优先 `~/.dsh/skills/commit-report/SKILL.md`，不存在时读仓库内的 `commit-report/SKILL.md`；两者都没有则报告并转人工确认；
2. 按其 §2 分析变更、匹配风格，生成 commit 信息草案；
3. 交付三样进入审阅要素：**文件清单**、**提交意图**（一句话：这一笔是什么功能）、**未纳入清单**。commit message 由这一环节按 `commit-report` 的规则生成，本技能不写 message、也不复制它的风格匹配规则；
4. **会话级授权即为本次审阅的确认**——自动模式下列出上述要素后直接执行提交，不逐次等待回应；
5. 未获授权，或用户要求逐笔确认、要求先看文案时，停在 `commit-report` §3 的两区展示等回应；
6. 本技能不触发 push。

**已知陷阱（Windows）**：`.git/COMMIT_EDITMSG` 带 Hidden 属性时，Git for Windows 报 `fatal: could not open '.git/COMMIT_EDITMSG': Permission denied`，提交无法进行——`attrib -h .git\COMMIT_EDITMSG` 后重试即可。iCloud／外置盘同步过的仓库常带这个属性。

## 五、硬红线

已获授权也拒绝自动执行，命中即中止并报告原因：

1. **凭据零入库**——按 `references/exclusions.md` 的凭据形态逐条核对 §三 解析出的**全部**路径（文件名与内容特征各扫一遍），命中即中止；任一路径解析失败同样中止，不跳过。
2. **破坏性 git 操作**——`git init`、删除文件、`git clean`、`--no-verify`、force push、amend 或 rebase 已推送提交、`reset --hard`、`checkout -- .`。

需要执行这些动作时，报告「这属于硬红线范围」，并请用户另行显式指示。

## 六、干跑

**何时跑**：首次在某仓库实战、授权边界不明（不确定用户授权了本仓库）、单次改动文件数 >20 或 diff >1000 行、用户说「先看看你会提交什么」。

**输出**：

```
[干跑] 仓库 <path> ｜ 分支 <branch> ｜ 上游 <upstream>（领先 N）
提交单元：<一句话意图>
信号来源：<用户验收／测试全绿／spec 条目／兜底>
将纳入（K 个文件）：
  M  <path>
未纳入（M 项）：
  <path>  — <原因：未闭合单元／垃圾文件／红线拦截>
```

干跑只读 `git status`、`git diff --stat` 与文件头。

## 七、完成后报告

每笔提交落定后报告：

1. 提交单元的信号来源与提交意图；
2. commit 哈希（完整 SHA）、主题行、文件统计（files changed / insertions / deletions）；
3. 未纳入清单；
4. 与上游的关系（领先 N），并注明 push 未执行——需要推送时请显式指示；
5. 发现 `.gitignore` 缺口或 `.git/` 内部污染时，作为独立建议列出。
