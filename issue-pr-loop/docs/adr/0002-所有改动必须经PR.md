# 所有改动必须经 PR，纯文档也不开例外

主干只接受来自 PR 的改动。这条约束覆盖代码、配置、数据迁移、门禁清单、CI 配置、文档、错别字修正，以及技能仓库自己的 SKILL.md。唯一的例外是进不了仓库的操作（服务器手工命令、线下配置），那种必须在 issue 里留下可复制粘贴的命令、执行人和原始输出。

「纯文档可以直推」的方案被否决，理由是例外会膨胀：档口一旦打开，下一个理由就是「只改一行」「只是个注释」「赶时间」，而判断「算不算纯文档」的成本比开一张 PR 还高。真实项目里的数字也支持这个取舍——5 天 153 个 PR、151 个已合并、502 次提交，平均每 3.3 次提交一张 PR；开 PR 不是这套流程的瓶颈，评审积压和门禁基线才是。把 PR 成本降到很低（正文五段模板、纯文档免评审、一条命令开 PR）之后，它就不再需要例外。

PR 被定为唯一入口，不是因为它好看，而是因为它是唯一同时承载四样证据的单元：改动内容、门禁原始输出（跑在最新基线上）、新上下文的三段结论、回签计划。任何一样脱离 PR 就失去可核对性——门禁跑在谁的工作区说不清，评审看的是哪个版本说不清，回签对应哪次提交也说不清。同时 squash 合并让一张 PR 在主干里就是一个提交，回滚单位因此精确等于一张 PR；直推则会让一次改动分裂成不可单独撤销的若干提交。

代价是：每个改动都多一次开 PR、一次文本撰写、一次合并在队列里等。缓解方式是「让 PR 便宜」而不是「允许例外」——模板化正文、脚本生成评审派发、纯文档免评审、合并队列自动化排序。另一条被否决的方案是「只要求代码走 PR，文档走主干」：它把仓库切成两套历史，主干第一父链上会同时存在「可回溯到 PR」和「不可回溯」两种提交，对账脚本从此只能半信半疑。
