# 设计文档评审与编写 (Design Doc Review)

审计、验证、编写、重构与同步设计文档——用户（开发者）会迭代这些文档，其中的数值/schema 直接驱动后续实现。主场景：Web 开发（API 设计、数据模型、系统架构）；次场景：游戏设计（数值平衡、经济循环）。

## 何时使用

| 触发短语 | 动作 |
|---|---|
| "看一下 / 分析 / 评审 / 检查问题" + 某文档 | 全篇审计：通读全部内容，核验数值，交叉引用，标注 P0/P1/P2 |
| "拆分 / 重构 / 重写" 某文档 | 文档重构：拆分/合并并做内容不丢失验证（见 §6） |
| "写一份设计文档 / 提案" | 用「设计文档编写指南 → 章节骨架」编写新文档 |
| "数值对不上 / 检查数据" | 数值核验：用脚本重建表格、求和、交叉核对数量 |
| "同步 / 对齐" 多份文档 | 同步校验：grep 交叉引用，确保零残留漂移 |
| "还有什么没设计" | 覆盖度盘点：列出已有提案与缺失项 |

## 核心原则

以下规则来自用户纠正经验，必须遵守：

1. **先通读全文。** 每个章节、每张表格，在任何分析或操作之前。
2. **只审阅即只读。** 被要求审阅/分析时，不要改代码、跑构建、切分支、同步仓库。止步于分析 + 建议。
3. **未经用户明确指示，绝不 `git commit` / `git push`。** 生成/编辑文件可以；提交需要明确授权。
4. **权威文档优先。** 重构配套文档以对齐策划文档时，策划文档是最高权威。配套文档必须与策划需求 1:1 映射——零偏差。
5. **核心重构提案先行。** 结构性改动（数据模型、层级、阈值）→ 先写编号提案文档（标记 📋 待审批），获用户批准后，再改正式文档。

## 通用审计方法论

从领域无关的审计经验提炼的六项原则。无论文档是游戏策划、API 规范、系统架构还是 PRD，都适用。

### 1. 脚本验证

绝不信靠心算表格。用代码（`execute_code` / Python）重建每张表格并验证：
- 用程序对属性/数量表求和——逐行报告通过/失败
- 交叉引用表：一张表中的每个键必须在另一张表中可解析
- 核对声称的数量（"37 门课"、"33 个岗位"）与实际行数
- 检查序列的范围与单调性
- 通过项也要写出来——不只写失败项

### 2. 交叉引用完整性

设计文档是一张引用图。审计每条边：
- 实体→实体映射（证书→岗位、模块→表、endpoint→handler）
- 数量声称 vs 实际行数（"N 项" vs 表长度）
- 孤儿引用：指向不存在实体的键
- 陈旧引用：指向已重命名/删除实体的键

### 3. 严重性分级

| 级别 | 含义 | 示例 |
|---|---|---|
| **P0** | 破坏实现/玩法 | 算数漂移导致测试断言失效、不可达内容（阈值 > 最大值）、孤儿引用、矛盾状态规则 |
| **P1** | 逻辑冲突或规则未定义 | 状态机边界、取消时的费用处理、公式参数未定义、语义含糊 |
| **P2** | 缺数据源 / API 未定义 / 缺流程 | 无 catalog/list API、无响应 schema、无创建流程、缺迁移计划 |

### 4. 整改迭代

严格按优先级顺序修：**P0 → P1 → P2**，绝不跳级。

每一级之后：
- 进入下一级前**先验证修复**
- 在权威文档**和**配套文档**两处**更新版本 + 变更记录

（跨文档零残留验证与重构验证统一见 §6）

### 5. 核心重构提案先行

核心系统重构（数据模型、层级、阈值映射、版本规划）按此流程：

1. **写编号提案文档**（如 `NN-<功能名>设计方案.md`，标记 📋 待审批）
2. **写文档前用脚本核验每个数值**
3. **包含**：完整结构、完整表格、数值证明、旧→新映射、数据结构影响、测试影响、编号待定项且每项带 ✅ 推荐答案
4. **等用户批准**——不要动正式文档
5. **批准后**：一次性同步正式文档，更新版本 + 变更记录，验证零残留

### 6. 文档重构验证

拆分/合并文档时（含"README → 多 MD 文件目录"、"移动文档目录"两类常见操作）：
- **验证内容不丢失**：用源文档的一组锚点关键词 grep 新目标；每个锚点必须出现在 ≥1 个文件中
- **零残留验证**：grep **所有**相关文档中的陈旧/错误内容模式（旧版本号、陈旧功能引用、已删内容遗物、重命名实体不一致），用精确编辑清除全部残留
- 为每个文件添加导航头（索引链接 + 上一/下一链接）
- 仓库根目录已有 `README.md` 时，不要在子目录里再建一个
- 用 `NN-` 前缀编号文件以保证稳定排序；`00-` 作概览
- 过大的静态表格 → 抽到独立编号文件；主文档保留概览 + 指针
- 重新解析写出的输出，确认落盘数量与预期一致
- **移动目录陷阱**：目标已存在时，普通 `mv src dst` 会嵌套为 `dst/src/`——用 `mv dst/src/* dst/ && rmdir dst/src` 修正；移动后双向修复相对链接，用负向 lookbehind grep 找真残留（排除子串误报）

最终门禁：所有整改完成后，确认**全项目树零残留**。

## 设计文档编写指南

### 章节骨架

每份设计文档（无论领域）都应包含：

1. **背景与目标** — 解决什么问题、为什么是现在
2. **数值设计 / 数据模型** — 所有表格、schema、枚举。每个数值入表前必须脚本核验。标注核验方式（"脚本核验" / "手算" 并注明局限）。
3. **动作与接口 / API 设计** — 新动作、endpoint、请求/响应 schema
4. **前端表现 / 用户体验** — 用户如何看到/与之交互
5. **测试影响** — 需要编写/更新哪些测试
6. **实施建议** — 分阶段方案、依赖、工作量估算
7. **待定项** — 未决事项，每项带 ✅ 推荐答案
8. **已知问题台账**（如适用）— 编号，跨版本持久

### 待定项格式

```
❓ Q1 - <问题标题>：<问题正文>
  ➡️ ✅ 推荐：...（理由）
  状态：⏳ 待确认 / ✅ 已确认（用户调整：<变更>）
```

规则：
- 每个待定项**必须**有 ✅ 推荐答案（绝不留空）
- 批量确认用极简表达："全部确认" = 接受所有文档的所有 ✅
- 批量中单项覆盖："Q1 改为 X，其他确认" = 除 Q1 用用户值外全部接受
- 覆盖之后：扫整篇文档找被取代的旧值，替换每一处出现，再断言零残留

### 脚本核验要求

设计文档中任何数值、数量或映射表格，在写文档前**必须**用代码验证。验证脚本应：
- 从源数据重建表格
- 与每个声称的合计求和/比对（流转中的数值集合常有 3 套以上）
- 检查交叉引用可解析
- 检查范围与单调性
- 同时报告通过项与失败项

### 同步检查清单

设计文档获批并同步进正式文档后：
1. **在全项目树 grep 新系统关键词**
2. **确认命中只出现在预期文件中**（权威文档 + 配套文档）
3. **确认无关文件中 0 命中**（同时抓到漏同步与误改）
4. 在权威文档**和**配套文档**两处**更新版本 + 变更记录
5. **核对已知问题台账**已覆盖此前发现的所有 P0/P1

## 通用陷阱

以下 5 条贯穿所有设计文档工作；具体项目级陷阱见 `references/common/pitfalls-catalog.md`（持续扩充）。

1. **单文件补丁不完整。** 只改一个文件就宣布完成，会漏掉其他文档中的陈旧内容（同步文件、README、references）。定稿前务必 grep 全项目树找残留。

2. **优先级顺序是强制的。** 未完成 P0/P1 不得从 P2 跳到 P0。跳级会留下未解决的基础冲突。

3. **跨文档的陈旧模式清理。** 设计变更发生时，所有引用该内容的文档都必须更新。用精确 grep 模式（具体功能引用、已删实体名、重命名项）——不要用会匹配无关内容的宽泛模式。清理后断言零残留。

4. **版本号规则冲突。** 当用户选定的版本与项目自身版本规则矛盾时，在方案头部记录两条路径 + 决策点。不要悄悄二选一。

5. **权威文档优先。** 重构配套文档以对齐策划文档时，策划文档是最高权威。每个设计元素必须 1:1 映射到一条策划需求——零偏差。无法映射的设计标 P1。
