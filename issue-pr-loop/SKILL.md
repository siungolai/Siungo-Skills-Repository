# issue-pr-loop：改动只有一个入口，就是 PR

> ⚠️ **触发加载检查**：收到任何「把这几件事拆成 issue / 开单派活 / 并行开发 / 立一套 PR 与评审规矩 / 谁来做回签」类意图时，**先确认本技能已加载**——若本技能不在当前会话的可用技能列表里（技能快照可能早于本技能安装或更新），先用当前环境的技能加载机制加载它，然后按其流程执行。切忌在未加载技能的情况下直接开单、直推主干或合并 PR。

定位：本技能管**改动的入口、队列与证据**——单子怎么切、活怎么分层派、改动怎么进 PR、门禁在哪跑、评审交给谁、合并怎么排队、状态怎么用标签表达。它不教怎么写技能（`skill-authoring`）、不教怎么改领域模型（上游技能 `domain-modeling`）、也不替用户做技术决策（那是 `grilling`）。核心是一条硬律：**主干只接受 PR，PR 只接受证据**。并行能持续则靠另外三件事——单子能独立、依赖先摸清、合并只排队。PR 契约细则见 [`references/pr-contract.md`](references/pr-contract.md)，流程细则见 [`references/flow.md`](references/flow.md)，台账与门禁守卫见 [`references/ledger-and-gates.md`](references/ledger-and-gates.md)，实测基线与反例见 [`references/case-book.md`](references/case-book.md)，版本历史见 [`references/version.md`](references/version.md)。

**来源**：提炼自一份公开的并行协作实录（wiredraw 5 天 502 次提交、153 个 PR 中 151 个已合并）——数字与形态见 `references/case-book.md`。那份实录的 PR 是流程里的必经一环，不是「改完顺手提一下」的锦上添花；本技能把它固化成本仓库的硬约束。

## 1. 何时使用

| 情形 | 动作 |
|---|---|
| 「这几件事开成 issue」「一轮审计 / 一轮真机出了 20 个问题」 | 走 §4 开单，一次集中产出 |
| 「先把方案定下来」「plan 写哪儿」 | 走 §4 的 plan 追评 |
| 「几个会话一起改」「并行开跑」 | 走 §5 摸依赖分层、一 PR 一分支 |
| 「开 PR / 评审走了没有 / 谁来评」 | 走 §6 与 §8 |
| 「能合了吗」「几条 PR 一起进主干」 | 走 §7 与 §9 |
| 「怎么防止有人直接推主干」「规矩怎么落地」 | 走 §11 |
| 「合并后要回签吗」「这张单能关吗」 | 走 §10 |
| 「换个会话接手」「让新人 / 新 agent 上手」 | 走 §13 |
| 「改代码 / 写设计文档 / 提交推送本身」 | 不属于本技能；分别交给实现会话、`design-doc-review`、`commit-report`（但**它们的产出必须回到本技能的 PR 通道**） |

## 2. 三条硬律

1. **PR 是唯一入口**：任何落进主干的改动都必须来自一张 PR。禁止 `git push origin main`、禁止本地改完直接让人拉、禁止「先合了再补 PR」。连纯文档、连只改一行、连技能仓库自己的文件也一样——例外只有一种：改不动物理世界、进不了仓库的操作（服务器手工命令、线下配置），那种必须在 issue 里留下可复制的命令与执行人，否则视为没发生。
2. **一张 PR = 一张单**：PR 与 issue 一一对应，标题带单号。一张 PR 改了两件不相关的事就拆——它的回滚单位就不再是一件事。
3. **主干只接受排队合并**：同一时刻一条 PR 进主干；门禁必须跑在**最新主干**上；合并前重跑、合并后主干再跑一遍。

**为什么必须走 PR**（四句，写清楚才守得住）：PR 是唯一同时承载「改动内容 + 门禁原始输出 + 评审结论 + 回签记录」的单元；主干永远能回到上一个合并点，回滚单位就是一张 PR；多个并行会话彼此看不见，PR 是它们之间唯一可审计的交接面；没有 PR，门禁跑在谁的工作区、评审看的是哪个版本、回签对应哪次提交，全都说不清。

## 3. 八阶段流程

| # | 阶段 | 产出物 | 判据 | 不通过 |
|---|---|---|---|---|
| 1 | 开单 | issue 正文四要素 | 另一个会话照做即可复现 | 打 `needs-repro` |
| 2 | plan 追评 | issue 下的一条 plan 评论 | 读完正文 + plan 可直接开工 | 补 plan，不开分支 |
| 3 | 分支 | `<type>/<单号>-<slug>` + worktree | 一分支只服务一张单 | 拆单，不共用分支 |
| 4 | 开 PR | PR 正文五段齐全 | 无 PR 就不许推主干 | 补正文 |
| 5 | 门禁 | PR 上的全量输出 | 全部 required 绿 | 修到绿，不许「先合后修」 |
| 6 | 评审 | 新上下文三段结论 | `APPROVE` 且证据含评审人自跑输出 | 打回，改完重派 |
| 7 | 合并 | squash 进主干 | §9 七项检查全过 | 停在队列里等 |
| 8 | 回签关单 | 真机复跑原始输出 | 执行者 ≠ 修复者 | 挂 `needs-live-verify` |

八个阶段里**只有合并这一步是串行的**，前六步可以十条线同时跑；也让**没有人是闸门**——评审交给新上下文，回签交给发现者或另一个新会话。凡是要维护者逐张点头的环节都会变成队列瓶颈。

## 4. 开单与 plan：PR 的上游

一条 issue 只装**一件能独立验收的事**。判据三条同时成立才算合格：**能单独跑门禁**、**能单独合并**、**能单独回滚**。任何一条不成立就继续拆（拆分信号表见 `references/flow.md` 的「开单与拆分」一节）。

- 母单先定范围，子单正文首行带 `Refs #<母单号>`；
- 正文四要素：**现象 / 期望 / 复现命令 / 影响面**。复现命令先自己复制粘贴跑通，再补证据；
- 批量出单：一次审计或一轮真机集中产出一批，不要边想边写；
- plan 写在 issue 里当评论，不写进聊天：改哪些文件、为什么是这几个、门禁怎么跑、失败怎么回滚、验收谁做。

**判据**：新会话读完 issue 正文 + plan 即可开工，不必回看对话。开不出这样的单，就不该开分支。

## 5. 分支：一 PR 一分支，主干只读

- 分支命名 `<type>/<单号>-<slug>`，`type` 取 `feat` / `fix` / `refactor` / `docs` / `test`；
- 一个 worktree 一个目录，坏了删掉重来，不共用工作区；
- **主干分支（`main` / `master` / `slim`）在任何会话里都是只读的**：可以 `fetch`、可以 `rebase` 到它上面，不能在上面提交，更不能推上去；
- 已进入评审的分支**不许 force push**：要改就追加提交，让评审人看到「改了什么」；合并时由平台 squash，主干里仍是一个提交。

**判据**：`git rev-parse --abbrev-ref HEAD` 永不等于主干名（除非你只是在读）；主干上的每个提交都能追到一张 PR。

## 6. PR：唯一交付单元

标题 `<type>(<scope>): <一句话>`，末尾带单号，例如 `fix(progress): 未传完时进度环已画满 (#378)`。正文五段，缺一段就不进评审队列（完整模板见 `references/pr-contract.md` 的「正文五段」一节）：

| 段 | 写什么 | 判据 |
|---|---|---|
| 问题 | 对应单号与现象，一行；行为类只能写 `Refs #<单号>` | 不读 issue 也知道修什么 |
| 改动 | 文件清单 + 每处一两句 | 与 plan 不一致处必须写明原因 |
| 验证 | 自己怎么验的：新增/改了哪些用例，手工步骤是什么 | 说得清「红在哪、绿在哪」 |
| 门禁 | 门禁清单的全量原始输出，逐条贴 | 出现「已通过」三个字即不合格 |
| 回签 | 行为类：待 `needs-live-verify` 与复跑命令；纯文档/纯重构：不涉及 | 与 §10 的关单写法一致 |

硬性要求：一张 PR 只动一个主题；正文与分支必须同步（开着 PR 又在本地改而不推，等于让评审看旧代码）；门禁红不许写成「后续会修」；合并方式统一 squash，使**一张 PR 在主干里就是一个提交**——这样 `git revert <那个提交>` 就是完整回滚。完整契约见 `references/pr-contract.md`。

**判据**：随便抽一张已合并的 PR，能只看它一个页面说清「为什么改、改了什么、怎么验的、谁评的、回签了吗」。

## 7. 门禁：在 PR 上跑，跑在最新基线上

门禁清单的唯一事实源是仓库的机器可读清单（`scripts/gates.json` 或等价物），**PR 读它，文档不复制命令**（清单格式与纪律见 `references/ledger-and-gates.md` 的「门禁清单的唯一事实源」一节）。

- 三个时点必须跑：开 PR 时、评审要求补改后、**合并前在最新主干上重跑**；
- 门禁红就修，不许降级门禁来变绿——放宽门禁要单独开单、单独走评审；
- PR 上贴的必须是原始输出，评审人会拿它跟自己复跑的结果对照，对不上即为 CHANGES-REQUESTED。

**判据**：合并那一刻，PR 上最新一次门禁输出对应的基线 = 当时的主干。对不上就重跑。

## 8. 评审：外包给新上下文

派评测人一律**新上下文**，且执行线与评审人**不得是同一个会话**。派发文案由脚本生成，不手写——手写必然夹带提交者的说法（「只是小改」「测试过了」），事后无法核查。派发物料只给 PR 编号、分支名、改动文件清单、门禁命令；**不给 PR 正文**，评审人自己去读。

结论三段，缺一段视为未评审：

```
结论：APPROVE / CHANGES-REQUESTED
复核动作：<亲自跑了什么、读了哪些文件>
证据：<门禁原始输出 / 文件行号 / 反例复现>
```

**免审只有一种**：纯文档或纯重构，且 PR 正文首行写明「纯文档」或「纯重构」并贴门禁绿。免的是评审，**不是 PR**——它照样要开 PR、照样不许直推。

**判据**：结论行可被机器 grep；证据里至少一样是评审人自己跑出来的，不是抄 PR 正文的。

## 9. 串行合并：改的时候十条线，合只有一条队

同一时刻只允许一张 PR 进主干，合并前逐项过这张检查表：

1. 评审结论 = `APPROVE`，三段齐全，且证据可复核；
2. 门禁在**最新主干**上重跑全绿，输出贴在本 PR；
3. 本 PR 只对应一张单，正文五段齐全；
4. 行为类用 `Refs`（不是 `Closes`），且已在正文写明回签计划；
5. 合并方式 = squash，提交标题带单号；
6. 存活 PR 数未超上限（实测基线 10，超出先合不合新）；
7. 合并后立刻在主干上跑一遍门禁，红了下一条线全部暂停。

原因一句话：门禁要跑在最新主干上，两条 PR 同时进主干，谁先谁后都得重跑。**排队合并反而更快。**

## 10. 回签与关单：行为类不许自签

`Closes` 只给**纯文档与纯重构**。凡改动运行时行为（含配置、数据迁移、对外输出），一律 `Refs`，合并后挂 `needs-live-verify`，由**发现者或另一个新会话**在真机上复跑复现命令回签，回签通过后才关单。**修复者不能给自己回签**——自签等于取消真机验收。

**判据**：每张行为类单的关闭理由里有一条真机回签记录，执行者 ≠ 修复者，且引用了那张 PR。

## 11. 把规矩变成机制

只写在文档里的规矩会被绕过，尤其在自己赶进度的时候。三层，从软到硬，缺一层都算不上「强制」：

1. **平台分支保护**（首选）：主干要求「必须经 PR 合并」+「必需检查通过」+「禁止 force push」+「禁止直接推送」。GitHub / GitLab 都在仓库设置里，一次配好长期有效。
2. **本地钩子**（兜底）：装一个 `pre-push` 钩子，任何指向主干分支的推送直接失败退出。它挡的是「我忘了」，不是「我要违规」——所以还要第三层。
3. **对账**（可审计）：定期看主干第一父链上每个提交有没有对应的 PR 号；发现孤儿提交就是一次违规，补开 PR 或在 PR 里说明并记一笔。对账命令与钩子形态见 `references/pr-contract.md`。

**判据**：让一个不知道这套规矩的会话去「直接 push 到 main」，它成功不了。做到这一步，PR 才从「约定」变成「机制」。

## 12. 状态与标签

状态不靠人记，靠标签表达；谁空闲谁捡，计数就是待办清单。标签表、离开条件与每轮收口要读的三个数字见 `references/ledger-and-gates.md` 的「标签就是任务队列」一节。

- 一张单同时最多两个标签，超出的标签说明这张单没拆干净；
- 标签不表达进度百分比——进度体现在「有没有 PR、门禁绿不绿、有没有回签」；
- 报告里只报各标签计数，不报「正在努力推进」这类状态描述。

## 13. 记忆外置：接手只要四个文件

流程状态全部落在仓库里，不落在会话记忆里。基线是四个文档 + 一个门禁清单 + 两个脚本（评审派发、拒绝直推主干），职责与落点见 `references/flow.md` 的「记忆外置」一节。

接手六步：读总纲（只看红线和八阶段）→ 找一张已关闭的 issue 看四要素 → 看它的 plan 评论 → 打开对应 PR 看评审结论 → 自己开一张只有现象与复现的单 → 用派发脚本派一轮评审。第六步走通即进入队列。

**判据**：一个零历史的新会话能在六步内产出一张合格的单，并派出一次合规的评审。

## 14. 安全边界（硬性，任何路径下均适用）

1. **不替用户开 PR、合并、推送**——这三件都是不可逆动作，须用户明确授权；授权一次只覆盖一轮，不覆盖下一轮。
2. **不绕过 PR**：包括「只改一行」「只是文档」「先合了再补 PR」「本地改好让用户自己提」——全部禁止。纯文档免的是评审，不是 PR。
3. **行为类不许 `Closes` 自关**——见 §10；自签等于取消真机验收。
4. **不改门禁清单去让红变绿**——放宽门禁必须单独开一张单并走评审。
5. **不 force push 主干、不删除别人的分支、不改别人的 PR 正文**。
6. **同一文件不同层是违约**——发现已同层并行改同一文件，立刻停一条线、等前一条合完再继续。
7. **不把对话历史当交接材料**——没写进单子或 PR 的决定等于没发生。
8. **派发文案不许手写**——手写会夹带提交者说法，评审结论失去独立性。

## 15. 完成后报告

一轮（开单 / 派活 / 评审 / 合并 / 回签）收口时一次性报告：

1. **本轮产出的单子**：新建 / 关闭 / 新挂标签各几张，编号范围；
2. **分层与派发**：本轮几层、哪些单同层、有无同文件冲突；
3. **PR 状态**：存活 PR 数、每张的门禁状态与评审结论（APPROVE / CHANGES-REQUESTED / 未评）；
4. **合并记录**：合并了哪几张 PR（编号 + squash 提交号）、合并前最新基线的门禁输出；
5. **PR 合规**：本轮有无直推主干、有无孤儿提交（**必须报 0，报了非 0 就是事故**）；
6. **回签与遗留**：`needs-live-verify` 剩余清单及各自下一步；
7. **台账更新**：`README` / `CONTRIBUTING` / 门禁清单是否已同步（未同步要说明原因）。
