# 陷阱目录（项目特定陷阱库）

来自游戏与 Web 项目设计文档工作的项目特定陷阱。这些**不是**通用陷阱（通用陷阱在 SKILL.md）——这些是真实审计中暴露的具体项目级坑，绝不能再踩一遍。随审计持续扩充，条数不在此写死（避免与引用处漂移）。

---

## 代码与脚本陷阱

1. **`package-lock.json` 没进 `.gitignore`**：`npm install` 修改了 `package-lock.json`，工作树因此显示为脏。锁文件本应提交（标准做法），但要知道 `npm install` 之后工作树会看起来是脏的。

2. **Oxlint 警告很吵**：`react(only-export-components)` 会对同时导出组件和辅助函数的文件触发（很常见的模式）。这些是 `warning` 级，不阻塞构建；不要当错误处理。

3. **`npm test` 的时间敏感测试不稳定**：`StatisticsPage.test.tsx` 中的测试因本地时区与 UTC ISO 字符串不匹配而失败。向测试函数注入固定的 `now`，不要依赖 `new Date()`。

4. **`execute_code` 的 f-string 正则陷阱**：`f"...{'✅' if re.search(r'\| X \|', s) else '❌'}..."` 抛 `SyntaxError: f-string expression part cannot include a backslash`。把模式预编译成变量，在 f-string 内用 `pat.search(s)`；或把匹配放到 f-string 之外，只插值布尔结果。

5. **锚定台账计数验证**：对**整篇**文档数 `^(\d+)\. \*\*` 是错的——未来规划的编号项也会被匹配。先按 `## ⚠️` 切分，**再**在台账段内计数；报告重复项。

---

## Markdown 编辑陷阱

6. **Markdown 表格补丁吞换行**：替换多行表格块时若丢掉两行之间的换行，会静默合并成一行（`| a |…|| b |…`）。任何表格补丁后都要复查周边行；发现损坏立即把被合并的行重新拆成两行。

7. **扩容后的陈旧计数清理**：改一个计数（10 类 → 32 类）会在**同一**计数短语下留下残留，遍布 README、总览、规划等所有引用位置。要全仓库 grep 旧短语，不只是你改的那个文件。陷阱：**同前缀不同功能**——功能 A 从 10→32 时，功能 B 的"10 类"计数绝不能被误改；用精确到功能的模式，并验证清理后其他功能的计数仍然完整。

8. **移动目录残留要用负向 lookbehind**：把 `docs/` 替换成 `../archive/docs/…` 后，grep `docs/` 仍显示旧计数，因为新路径**包含**这个子串。用 `(?<!\.\./archive)docs/` 找真正的残留。

## 同步与并发陷阱

9. **批准后的同步要防并发**：批准后要 patch 正式文档之前，先 grep 新系统关键词——并行/上一轮会话可能**已经**部分同步过了。补丁报 "Could not find a match" 往往意味着文件被并发修改——重新读取并重新搜索文件当前的真实内容。

10. **盲追加导致台账条目重复**：往已知问题里追加编号条目时不检查已有编号，会造出重复（两个 #15 行）。修法：去重为一行，验证唯一性（`grep -c "^15\\. " file` → 必须为 1）。

11. **首个验证脚本误报**：全篇正则匹配到了未来规划的编号项，把 11/12/13/14/17/18 误标为重复。务必锚定到台账段。

12. **已知问题台账纪律**：每次审计都必须交叉检查文档**自己的**已知问题章节是否覆盖了**所有**此前发现的 P0/P1。未被跟踪的发现会静默腐烂；发现时补录进去。

## 文档重构陷阱

13. **单文件补丁不完整**：只改当前在编辑的那个文件就宣布完成，会漏掉**其他**文档里的陈旧内容。定稿前 grep 全项目树找残留。

14. **README ↔ 拆分文档漂移**：文档重构加后续编辑之后，README 与拆分文档会分叉。审计时要在**两边**都 grep 陈旧锚点，不只查主文档。还要核对标题与表格范围是否一致（追加一个阶段后，标题写"P0–P9"但表格已是 P0–P10）。

15. **子目录 README 重复**：仓库根已有 README.md 时再在子目录建一个，被标记为重复。要么删掉子目录索引并改名，要么改掉所有指向它的导航链接。

16. **移动文档目录——目标已存在**：普通 `mv src dst` 会嵌套成 `dst/src/…` 而不是移进 dst。修法：`mv dst/src/* dst/ && rmdir dst/src`。

## 数据与模型陷阱

17. **层级重命名的术语撞车**：当新层级用了代码中已有的英文术语（新"科目" = Course，而代码里的 `Course` 是叶子节点）时，要把选择显式摆出来——严格代码镜像（全量重命名 + 存储键升版本，约 20 文件波及面）vs 仅 UI 命名。验收要包含对每个已删标识符的 grep 零残留门禁。

18. **绝不要把旧 localStorage 键复用于语义不同的实体**：只校验部分字段（id+name）的校验器会静默接受旧 schema 下写入的历史行。淘汰旧键，引入全新键。

19. **跨系统冗余（成就 vs 日记）**：两个系统看起来内容重复时，**不要猜**——用脚本映射它们的条目列表并量化重叠度（成就条件 ↔ 日记事件类型；结果例如 9/20 = 45%）。然后给出选项（A 分工并存 / B 削减 / C 合并）让用户选。取消跨写联动，避免一个系统触发另一个。

20. **同步后的验证 grep**：设计获批并同步进正式文档后，全仓库 grep 新系统关键词，确认命中只出现在预期文件中。一条命令同时抓到漏同步和误改。

21. **功能头脑风暴 → 规划池 流程**：用户要功能点子时，给分层建议（🔥 高推荐 / ⭐ 中推荐 / 🚀 远期）并带成本 + 落地阶段提示——**不要改任何文档**。当用户说"全部纳入规划"时，把未来规划章节重构为主题分组，**保留所有原有项**，把该池声明为"不阻塞主线"。

## 验证陷阱

22. **三套数值集合在流转**：文档里有**三套**不同数值（原始策划案、标注的"实算"、真实合计）。必须把**所有**集合都列出来并显式核对——不要只挑一套。

23. **按消费方子集做可达性**：学位/学科从共享课程池中各取子集，所以每档门槛都要按**每个消费方自己的子集**配平——全局求和过关会掩盖某个子集不达标的学位。

24. **修复决策：降阈值，不加强源头**：某岗位门槛要求属性 ≥120，但可达最大是 118。修法：降到 118。理由：累计求和已经过脚本核验；在没有底层条目表的情况下改一个已核验的累计值，会制造**新的**数值漂移。

25. **修复决策：改造孤儿，不新增实体**：某证书解锁了一个不存在的岗位。修法：把它改为已有证书的前置。新增岗位会波及所有引用"岗位总数"的计数。

26. **版本路线的可达性硬约束**：基础版属性上限（X/Y/Z）必须能解锁基础岗位档位。如果不能（X < 门槛），高段位必须**连同课程一起**延后——不带课程上线 = P0 bug（岗位存在但属性不可达）。

27. **金币溢出检测**：交完所有学费/一次性购买后，结余是否只增不花？如果是（日结余 700+），修法是**强制消费**，而是自愿型娱乐/回收口（按活动规模定在回收日结余的一定比例）。

28. **主数据文档覆盖审计**：把**每份**已批准提案的新增面与主数据/结算文档交叉引用（动作表、状态响应结构、catalog 结构、数据表、参数形态；即 actions / state 字段 / catalog / 数据表 / 参数形态）。按类别给出通过/失败清单，然后逐个补缺口。

29. **奖励类功能的防通胀论证**：成就给 0 金币（纯 exp + 外观称号）以切断任何肝金币路径；日常任务金币绑定到消耗动作（学习/赚钱），免费动作（喂食/摸摸）只给 exp + 少量金币——否则免费配额变成免费钱，与商店经济冲突。

30. **多周期任务 v2**：给任务系统扩展周/月周期时，用**一张**统一表（如 `<table_name>` 或 `quests`）带 `period` + `period_key`（daily=date / weekly=ISO周 / monthly=自然月，唯一约束 user+period+period_key+quest_id），而不是三张表。周/月进度在**读时**从日计数器聚合。防通胀论证必须把**三层全部**求和。

31. **事件目录扩量（10→N→M）**：当用户把事件**数量**推高时，预期多轮升级，不止翻倍。重构要点：(a) 领域分组，(b) 粒度分类（首次/每次·里程碑/读时推导），(c) 显式防刷屏规则，(d) **每一轮**都脚本核验（唯一性 + 可达性 + 首年估算 + 存储），(e) 全仓库扫旧计数，**排除**同前缀其他功能的计数。

32. **中期批量提案关联图**：设计一批相互关联的功能时，**先**画关联图。在已批准的目录里预留钩子事件（如日记/通知/事件流系统的占位槽、外部系统接口位），让后续提案插进来不用返工。效率计算走服务器权威（按服务器时间，不是客户端）以击败时钟篡改。

33. **跨系统冗余审计（方案 A/B/C）**：两个系统内容重复时，量化重叠度（例如 9/20 = 45%）。给三个选项：A 分工并存（取消跨写、替换死事件、加定位对照表）、B 削减（砍掉一侧）、C 合并（一个系统两个视图）。最终 grep 必须显示联动短语零残留。

34. **核心系统重构 → 提案先行**：**先**写编号提案文档（标记 📋 待审批），包含完整结构 + 完整表格 + 脚本核验的数值证明 + 旧→新映射 + 数据结构影响 + 测试影响 + 编号待定项（每项带 ✅ 推荐答案）。批准前**不要**动正式文档。用户在迭代中会把范围往上推——预期多轮修订。

35. **时间线/事件扩量模式**：超大表（数百条）不能按单条发属性（数值会爆炸）→ 单位只给 exp/时间，**里程碑**在达到节点时发属性。重新验证新上限仍满足解锁阈值。不切实际的"全"成就降级为外观，不作门槛。

36. **批量新功能提案流程**：用户说「依次生成策划案，供我审批」时，每个功能生成**一份**编号提案文档，用固定骨架。批量批准用极简表达。批准后**一次性**同步正式文档。被问「还有什么没策划」时保持**覆盖度盘点**：✅ has-proposal / ⚠️ mechanism-locked-no-proposal / ❌ none。

37. **批量确认中的单项覆盖**：用户可能批准整个批次，但**除一个待定项**外要数值覆盖。执行：(a) 把被覆盖项重写为 ✅ 已确认 + 用户值 + 标注「（用户调整）」，(b) 扫整篇文档找被取代的旧值，(c) 把用户值带入正式文档同步，(d) 更新 references 文件为已确认值。

38. **版本路线规划**：当实现量感觉压不住时，把 P0–Pn 重构为可发布的版本路线，其中 V1.0.0 = 现有全部功能的基本实现。3 段式版本规则（两位数段、无第 4 段、bug 修复溢出顺延）。把每个 P 阶段 + 每份已批准设计文档都映射进一个版本。宣布 V0.1.0 为首个**可玩**版本。用脚本核验严格单调递增。

39. **功能分级 / 机制先行数据分批**：静态数据量巨大时，把每个模块拆成基础功能（V1.0.0 必须）vs 后续补充（V1.x 数据追加）。方法：(a) 数据量盘点，(b) **先**做可达性硬约束，(c) 版本内录入批次（≤40 行），(d) 总量不变，(e) 只对基础版做经济闭环检查。

40. **后端数据/存储规划章节**：新增自包含章节，覆盖 (a) handler→service→store 分层架构，(b) 按类别分组的表全景，(c) 读时计算的数据支撑，(d) 事务与幂等，(e) 数据兼容与迁移。

41. **回读正则必须锚定**：写盘后要用 `^### ([\u4e00-\u9fff]{2,3} [A-Z]{2})$` 重新解析条目行——宽泛模式会把数字子章节误匹配成假条目，导致计数崩掉。

42. **跨文档零残留验证**：每轮整改迭代后，grep **所有**相关文档中的陈旧/错误内容模式。用精确编辑清除全部残留。检测模式：旧版本号、陈旧功能引用、已删内容遗物、重命名实体的不一致。

43. **版本与变更记录要同时更新两份文档**：每轮整改迭代后，在**策划案**和**配套文档两处**都更新版本 + 变更记录。漏掉一份就会让它们失同步。
