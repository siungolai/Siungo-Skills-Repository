# agent-team-setup：按需求配置 DSH 智能体团队

> ⚠️ **触发加载检查**：收到任何「组个队 / 用团队做 / 分工开发 / 配置智能体团队」类意图时，**先确认本技能已加载**——若本技能不在当前会话的可用技能列表里（技能快照可能早于本技能安装或更新），先用当前环境的技能加载机制加载它，然后按其流程执行。切忌在未加载技能的情况下**直接组建团队**——席位、写范围与依赖边都还没经用户确认，事后返工的是整个团队。

定位：与 `commit-report`、`deploy-report` 同族——**先展示后动手**。区别在于它配置的是**开发者**（席位、写范围、共享任务板），而不是某一笔变更。团队只交付代码：提交归 `commit-report`、上线归 `deploy-report`、验收归 `code-review`，本技能一律不碰。宿主事实与硬约束见 [`references/dsh-constraints.md`](references/dsh-constraints.md)，席位与任务链模型见 [`references/team-model.md`](references/team-model.md)，版本历史见 [`references/version.md`](references/version.md)。

## 1. 何时使用

| 情形 | 动作 |
|---|---|
| 「组个队做 X」「用团队开发这个功能」「帮我配一个开发团队」 | 走 §2 起的新组建流程 |
| 需求是网页/前端/后端/全栈开发 | 用 `web` 预设：席位表、prompt 骨架、契约版式与验证命令探测顺序见 [`references/presets/web.md`](references/presets/web.md) |
| 团队已在场，要加/减席位、改任务、看进度 | 走 §7 停滞与生命周期 |
| 用户要审查、提交或上线 | 分别交给 `code-review`、`commit-report`、`deploy-report`，本技能不接管 |
| 改动只有一个文件、一个 bug、一段文案，或非开发任务（写文档、查资料） | 不组建团队，说明理由后按常规流程做 |

## 2. 启动前事实探测（自己查，不问用户）

1. **技术栈与包管理器**：读盘判定——`package.json` / `pnpm-lock.yaml` / `package-lock.json` / `pyproject.toml` / `go.mod` / `Cargo.toml` / `composer.json` 等，取第一个成立的；同时记下构建与启动脚本。
2. **目录结构与潜在分隔面**：列出顶层目录与源码根，标出天然可切的两侧（如 `src/client` 与 `src/server`、`app/` 与 `api/`），这是 §4 写范围的原料。
3. **验证命令（必须来自读盘，不许猜）**：按 [`references/presets/web.md`](references/presets/web.md) 的探测顺序找测试、静态检查、构建三类命令——`package.json` 的 scripts、`Makefile`、`pyproject.toml`、CI 配置、项目自述文档。记录到命令级；项目里没有的类别记为「无」，不编造。
4. **项目文档落点**：找 `CONTEXT.md`、`CONTEXT-MAP.md`、`docs/adr/`、`AGENTS.md`、既有的 `docs/spec/` 或 `.doc/` 目录。存在 `CONTEXT-MAP.md` 说明项目有多个上下文域，需先确定本功能属于哪个域；都没有则按 `docs/spec/<feature>.md` 建。
5. **功能范围与停止条件**：把用户口述的需求复述成一句话目标，并明确本次只做一个 ticket——**一次只开一队、只做一个功能**。
6. **工作区状态**：未提交变更、是否 git 仓库。脏工作区要在契约里声明：团队只在其写范围内动手，不代管未提交变更。

探测结果只用于算席位与写契约，**不落任何文件**——项目级事实留在会话里（用户没要求建档就不建档）。

## 3. 判定分支：组不组、组几席、怎么裁

1. **组队门槛**：功能需要同时改动 ≥2 个交付面（如前端与后端），或预计跨越 ≥3 个文件且有明确验收标准 → 组队。否则不组，说明理由后按常规流程直接做。
2. **席位裁剪**：默认五席——你（Lead）+ `web-planner` + `web-frontend` + `web-backend` + `web-reviewer`（只读）；只有单一交付面时裁掉对侧开发席；可选槽 `web-data`、`web-docs` **最多开一个**（含你总上限 8 席，见 [`references/dsh-constraints.md`](references/dsh-constraints.md) 的 §1「Team 的形态」）。
3. **`web-planner` 的保留判据**：用户已给现成 spec、或需求一句话就能穷尽时裁掉它，直接进构建。保留时它按 §5 的 Phase 1 产出 spec。
4. **写范围切法**（按目录切，逐目录点名到每个席位）：共享文件（配置、依赖清单、`README`、入口文件）**由你独占串行改**；构建产物与生成物不进任何人范围；每个文件恰好一个 owner。详见 [`references/team-model.md`](references/team-model.md)。
5. **核对席位与任务链一一对应**：每个座位都有它认领的任务，每个任务都有 owner；`verify` 任务的 owner 不能是实现任务的 owner。

## 4. 契约展示（展示后停下等待）

按 [`references/presets/web.md`](references/presets/web.md) 的骨架组织，**八项都要出现**（没有的项写「无」，不能省略整项）：

1. **需求摘要**：一句话目标 + 用户可验收的判据来源（现存 spec 路径，或「由 `web-planner` 产出」）；
2. **席位表**：席位名 / 角色 / 职责 / 写范围（逐个目录点名）/ 是否只读；
3. **共享文件归属**：声明由你独占改动的文件清单；
4. **任务图**：任务 ID + owner + 依赖边 + 每个任务的完成判据；
5. **验证计划**：探测到的验证命令（注明读盘来源）+ 由 `web-reviewer` 独立复跑；
6. **边界与停止条件**：本次只做一个 ticket、ticket 闭合即解散、组队期间普通子代理被禁用（上游 `code-review` 与 `research` 在此模式下失效）；
7. **开放问题**：探测不清、需要用户拍板的点（没有写「无」）；
8. **回应路径**（固定文案）：

```
请回复：
① 确认组建（按契约执行，范围外不做任何操作）
② 需要调整（改席位 / 改写范围 / 改任务链 / 其他）
③ 取消本次组队
```

用户回复②→ 改完**重新走 §4**；回复③→ 结束，不留成员、不建任务。

## 5. 组建与派活（仅在用户回复①后）

1. **成员命名**：lower-kebab-case、≤64 字符、不得为 `lead`；成员名在同一 Team 内**永久不复用**——解散后重开新队要用新名（如 `web-frontend-2`）。
2. **按席位表逐个生成成员**，`description` 写职责一句话，`prompt` 用 [`references/presets/web.md`](references/presets/web.md) 的骨架缝进该席位的写范围、验证命令、回报方式。角色差异**全靠 prompt**：生成接口没有模型、推理档位等参数可调。每生成一个核对一次名册，确认名字与职责符合契约再生成下一个。
3. **在共享任务板上建任务**：`team_task_create` 建任务时**不接受依赖边**，建完必须用 `team_task_update` 的 `set_dependencies` 补 `blockedBy`，并以 `expectedRevision` 做 CAS 快照比对。
4. **补边后回读任务板**，确认依赖图与契约一致、没有环、`verify` 的 owner 不与实现席相同。
5. **派活即回报**：任务初始无 owner，靠成员 `claim` 认领；在成员 `prompt` 里写清它该认领哪个任务 ID、完成后如何向你回报（见 §8）。

## 6. 构建期编排

1. **只做协调，不代写代码**：你的动作是看名册、看任务板、看邮箱、裁决阻塞；实现落在各席位的写范围内。
2. **等边沿，不等人**：`wait_agent` 只返回「等到了 / 超时」，**内容要再回读一次**；它观察的是调用开始之后的边沿，**绝不唤醒成员**。
3. **停滞处理（每次 `wait_agent` 空手返回后照做）**：① `list_agents` 看名册与状态；② `team_task_list` 看任务是否真的没动；③ 按此裁决——成员还在跑就继续等；任务 ready 却无人 claim 就 `send_message` 唤醒对应席位；成员失联或任务明显跑偏就用改派（**改派是你的专属动作**，只有 Lead 能调）；确实卡死就中断该成员并按 §4 重新展示。每个动作后回到①重新判定，不重复发同一条唤醒。
4. **依赖边就是闸门**：下游任务的 readiness = 所有 `blockedBy` 已 completed，而 readiness **不会唤醒成员**——所以 `spec` 一完成就要主动叫醒两侧开发席。
5. **实现席完成后先由你把关**：读它的 diff 与回报，确认落在写范围内、验证命令有实际输出，再让 `verify` 任务就绪。改动越界或证据不足就打回该任务（见 §8 第 1 条）。
6. **不代管提交与上线**：团队产出停在工作区；要提交走 `commit-report`，要上线走 `deploy-report`——那是你的会话动作，不是席位的动作。

## 7. 停滞与生命周期

1. **状态事实**：`wait_agent` 只等 running/provisioning 的对等体，**没有活跃对等体时立刻返回**；成员跑完一轮转 inactive 不等于任务完成（见 [`references/dsh-constraints.md`](references/dsh-constraints.md)）。所以「等」永远要配一次 §6 第 3 条的停滞处理。
2. **邮箱是私有的**：只有你能看到全体消息，**每个席位只看得到发给自己的**。要它回报就必须在它的 `prompt` 里指定「用显式消息发给 lead」；没指定就等于没有回报通道。
3. **审查席的独立性**：`web-reviewer` 只读、不写代码，按 §4 展示过的验证命令**独立复跑**，逐条比对可判真假的验收标准；它的报告显式发给你。
4. **终态**：`verify` 完成 → 逐条交你验收 → 按 §10 报告 → **解散团队（一次只开一队）**。解散不删除工作区产物；下一个功能重新按 §4 展示契约。
5. **中途扩范围**：用户在新消息里追加需求时，回到 §2 重算并**重新展示契约**，不在运行中的团队上悄悄加座位或加范围。

## 8. 打回与裁决

1. **审查未过 → 打回**：`web-reviewer` 用 `reopen` 把该实现任务从 completed 打回 pending（**CAS 会顺带清掉 owner**），报告里逐条列出未过的验收标准。原主重新 `claim` → 修完 `complete`。
2. **打回即闸门**：`reopen` 之后 `verify` 任务的 `blockedBy` 重新变为不满足，**打回不需要额外机制**——下游自动失去 ready，天然防重复审查。别手工删任务、别为打回新建任务。
3. **改派只能由你做**：成员失联或方向跑偏时用改派（Lead-only）；任务在 pending 或 in_progress 时才能改派，省略 owner 会退回 pending。
4. **审查席越界时**：它无权改代码、无权删任务；若它自行扩大审查范围，以契约的验收标准为准，把超范围部分记进 §10 报告的遗留项，不采信为打回理由。
5. **绝不为了让它过而放宽验收标准**：标准在 §4 展示时已经固定，中途改动必须回到 §4 重新确认。

## 9. 安全边界（硬性，任何路径下均适用）

1. **不提交、不推送、不部署、不删远端**：团队只改工作区文件；提交与上线分别归 `commit-report` 与 `deploy-report`。
2. **凭据与私有信息零入库**：席位 `prompt`、任务描述、spec 与报告中不得出现密钥、token、连接串口令、内网地址与私有路径细节。
3. **只在契约范围内动手**：不顺手改别人的文件、不清理无关文件、不临时加做未展示的任务；共享文件只能由你改。
4. **不为通过而放宽标准**：不跳过验证、不把未复跑的命令写成已通过、不把审查意见悄悄降级。
5. **不与宿主限制较劲**：生成成员或任务板报错时，先读错误码与名册再决定（成员上限、名字冲突、CAS 过期、任务图成环，判定见 [`references/dsh-constraints.md`](references/dsh-constraints.md)），**不换写法反复重试同一动作**；确实受限就报告并降级为单会话执行。

## 10. 完成后报告

1. **交付物清单**：新增/修改的文件，按席位归属分组；
2. **需求文档**：spec 路径（若本次有 planner）；
3. **任务结果**：每个任务 ID 的终态与 owner；
4. **验证证据**：跑过的验证命令 + 实际输出摘要（含审查席的独立复跑结果）；
5. **契约偏离**：实际写范围与展示时的差异（**没有偏离就明确写「无偏离」**）；
6. **遗留事项**：未修的低优问题、审查中未过的条目、需用户决策的点；
7. **下次开工**：提醒「下次组队要重新展示契约」，并说明团队已解散。
